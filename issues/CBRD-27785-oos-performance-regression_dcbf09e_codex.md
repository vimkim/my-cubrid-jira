## Description

### 큰 값을 heap 밖으로 옮기는 이유

OOS는 큰 컬럼 값을 heap record 밖의 별도 저장 공간으로 옮기고, heap에는 작은 record를 남기는 기능이다. 목적은 **heap page 하나를 읽을 때 더 많은 record를 함께 얻도록 heap 집적도를 높이는 것**이다.

PostgreSQL과 같은 취지로, heap에 남는 record를 한 page에 4개 담을 수 있는 크기까지 줄이는 것을 목표로 한다. 이 크기의 record를 채울 때, 갱신을 위한 빈 공간인 unfill space를 남기면 보통 3개 수준, 남기지 않으면 4개가 들어갈 수 있다. 즉 **page당 3~4개를 담을 수 있도록 유도하는 설계**이며, 3개와 4개의 차이는 unfill space를 남기는지에 따라 생긴다. record 크기를 정하는 기준 자체는 unfill space와 독립적이다.

이렇게 하면 큰 컬럼이 필요 없는 조회는 heap page만 읽어 여러 record의 작은 컬럼을 처리할 수 있다. 같은 수의 record를 읽는 데 필요한 heap page 수를 줄일 수 있으므로, 데이터가 메모리에 모두 들어가지 않아 디스크 I/O가 발생하는 조건에서 이득을 기대한다.

여기서 3~4개는 큰 가변 값을 충분히 밖으로 옮겨 목표 크기를 만족한 record를 기준으로 한 수용 목표다. 실제 page의 record 개수는 record 크기, 남은 빈 공간, 삭제 상태 등에 따라 달라지므로 모든 page에 항상 최소 3개가 존재한다는 보장은 아니다.

### 그 대신 일부 작업이 느려질 수 있다

이 정책은 기존에는 heap page 안에 들어가던 데이터도 큰 컬럼 값을 OOS로 옮길 수 있게 한다. 아래 표의 **2번(heap → OOS)**이 이에 해당한다.

이전에는 heap만 읽으면 되던 큰 컬럼을 이제는 별도 OOS 저장 공간에서 읽어야 한다. 값을 따라가서 읽고 조립하는 CPU 작업과 page 접근이 추가될 수 있고, INSERT·UPDATE에서도 별도 저장을 관리하는 비용이 든다. 특히 데이터가 이미 메모리에 있어 디스크 I/O 절감 효과가 작거나, 큰 컬럼을 매번 읽는 작업에서는 이전보다 느려질 수 있다.

**이는 heap 집적도와 I/O 효율을 얻는 대신 일부 작업의 비용을 감수하는 설계 trade-off다.** 따라서 2번에서 어느 정도 느려지는 것은 이 설계의 비용으로 감안한다. 비용은 작업 내용에 따라 달라지며, 허용할 성능 저하율을 이 문서에서 일률적인 숫자로 정하지 않는다.

### 이번 이슈는 1번과 3번의 CRUD를 다룬다

아래 화살표는 같은 데이터의 **OOS 기능 적용 전 → 적용 후** 저장 위치를 뜻한다. 한 번의 UPDATE 중에 저장 위치가 바뀐다는 뜻은 아니다. 기존 overflow는 큰 record를 행 단위로 밖에 저장하는 방식이고, OOS는 큰 컬럼 값을 따로 저장하는 방식이다.

| 구분 | OOS 적용 전 → 적용 후 | 성능을 해석하는 기준 | 이번 이슈의 범위 |
| --- | --- | --- | --- |
| **1번** | **heap → heap** | 저장 위치가 같으므로 CRUD 비용도 기존과 비슷해야 한다. 느려지는 원인을 조사·개선한다. | **CRUD 포함** |
| **2번** | **heap → OOS** | heap 집적도를 얻는 대신 별도 값 접근·관리 비용을 부담한다. 일부 성능 저하는 설계 trade-off로 감안한다. | **저장 정책에 따른 성능 차이의 개선은 제외** |
| **3번** | **overflow → OOS** | 기존에도 큰 데이터를 밖에 저장했다. 기존 대비 비슷하거나 나은 성능을 기대하고, 느려지는 원인을 조사·개선한다. | **CRUD 포함** |

**이번 이슈의 성능 저하 조사·개선 대상은 1번과 3번이다.** 2번의 저장 정책에 따른 비용은 heap 집적도 및 I/O 이득과 함께 설명한다.

### 왜 개선해야 하는가

1번은 OOS 값을 사용하지 않는 기존 작업이다. 이 경우까지 공통 처리 비용이 늘면 OOS의 이득을 얻지 못하는 사용자도 같은 CRUD에 더 많은 CPU와 시간을 쓰게 된다. 이미 확인한 SELECT 스캔의 추가 비용을 줄이고, 다른 CRUD에서도 같은 문제가 있는지 확인해야 한다.

3번은 기존 overflow를 OOS로 대체하는 경우다. 작은 컬럼만 읽을 때의 이득뿐 아니라 큰 값을 읽고 쓰는 작업의 비용도 비교해야 기존 방식을 대체할 수 있는지 판단할 수 있다. 여러 OOS 컬럼에 접근하면서 page 접근이 늘어나는 경우에는 그 비용과 원인을 함께 설명한다. 현재 3번 전체에 대한 독립 측정 결과는 없다.

## Investigation Scope

### 비교할 작업

1번과 3번에서 각각 다음 작업을 OOS 적용 전후로 비교한다.

- **INSERT**: 같은 데이터를 적재한다.
- **SELECT**: 작은 컬럼만 읽는 작업과 큰 컬럼까지 읽는 작업을 나눈다. 전체 스캔과 PK 조회도 구분한다.
- **UPDATE**: 작은 컬럼만 바꾸는 작업과 큰 컬럼 값을 바꾸는 작업을 나눈다.
- **DELETE**: 같은 수의 record를 삭제하고, 삭제 자체와 이후 vacuum 정리 비용을 구분한다.

선언된 컬럼 길이만으로 1·2·3번을 분류하지 않는다. 실제 heap·overflow·OOS 저장 상태를 확인한다. UPDATE는 변경 전후의 저장 위치를 모두 기록해, 저장 경계를 넘는 작업을 한 경로에 머무는 작업과 섞지 않는다.

데이터가 메모리에 모두 들어가는 조건에서는 CPU 비용을 비교한다. I/O가 발생하는 조건에서는 경과 시간, page 접근 수와 실제 디스크 읽기도 함께 확인한다. 쓰기 작업은 로그 양과 vacuum 상태를 기록한다.

변경하지 않은 OOS 값의 UPDATE 재적재 문제는 [CBRD-27230](https://jira.cubrid.org/browse/CBRD-27230)과 연결하여 중복 구현하지 않는다. rollback·vacuum 안전성은 [CBRD-27237](https://jira.cubrid.org/browse/CBRD-27237) 등 관련 이슈의 범위를 유지한다. OOS 비활성화·임계값 설정은 별도 정책 검토 대상이다.

## Current Results

### 완료한 것은 1번의 SELECT 스캔 개선이다

2026-10-27 독립 실험에서는 약 100B의 작은 record 20만 개를 사용했다. 세 비교 빌드 모두 heap에 20만 개, overflow에는 0개가 저장되었고, OOS 적용본에도 연결된 OOS 파일이 없음을 확인했다. 따라서 **1번(heap → heap)** 비교다.

`data_buffer_size=4G` 로 데이터를 메모리에 올린 상태에서 측정했다. 아래 수치는 경과 시간이 아니라 서버가 실행한 **CPU 명령 수(instructions)의 증가율**이다. 좁은 스캔은 정수 컬럼 하나를 집계하고, 여러 컬럼 스캔은 정수 두 개와 가변 컬럼 길이를 집계한다.

| 비교 | 좁은 컬럼 스캔 | 여러 컬럼 스캔 |
| --- | ---: | ---: |
| 수정 전 OOS 적용본 / 통합 전 기준 | 약 +5.12% | 약 +8.89% |
| 수정 후 / 통합 전 기준, 정순 측정 | +1.106605% | +1.362198% |
| 수정 후 / 통합 전 기준, 역순 측정 | +1.107484% | +1.362450% |

일반 heap 값을 읽을 때 OOS 전용 준비 작업까지 거치던 비용을 줄였다. 두 스캔 모두 이번 수정에 합의한 **CPU 명령 수 증가 2% 이하** 기준을 충족했다. 이 기준은 해당 1번 SELECT 스캔에만 적용하며, 다른 CRUD나 3번의 합격 기준으로 확대하지 않는다.

해당 패치의 기존 검증에서 SERVER_MODE·SA_MODE 빌드·설치, 집중 CTest 15/15, snapshot/vacuum 선택 검사 3/3, 추가 정확성 검사 4/4가 통과했다.

| 대상 | 현재 확인한 범위 | 남은 범위 |
| --- | --- | --- |
| 1번: heap → heap | 위 두 SELECT 스캔의 성능 개선·검증 | INSERT·UPDATE·DELETE와 나머지 SELECT 조건의 성능 비교 |
| 3번: overflow → OOS | 이번 이슈의 조사·개선 대상으로 지정 | CRUD 성능 비교, 저하 원인 분석과 개선·검증 |

일반 heap SELECT 스캔의 개선을 1·3번 CRUD 전체 완료로 해석하지 않는다. 전체 회사 CI, ASAN, HA와 대용량 I/O 성능 검증도 위 결과에 포함되지 않는다.

- [ ] 작은 컬럼만 읽는 조회, 여러 큰 OOS 컬럼의 조회, OOS 컬럼 5개 중 1개만 갱신, 단일·동시 CRUD 반복 중 필요한 범위를 승인하고 각 시나리오를 TC와 연결한다. 기존 +2% instructions 기준은 승인된 1번 SELECT 두 건에만 적용하고, 나머지 수치 기준은 별도로 합의한다.
- [ ] 승인한 조건으로 비교 TC를 구현·보강하고 정확성, 비교 revision·설정·실행 순서·cache 조건, 반복 측정과 원시 결과를 보존한다. 기존 하네스·실측을 재사용하고 실패·무효 측정·미실행 범위를 구분한다.
- [ ] 성능 TC를 넣을 performance 영역의 경로·runner·실행 주기·대상 branch를 담당자와 확정하고, TC PR의 리뷰·승인 후 실제 편입·병합을 PR과 merge commit으로 확인한다.
- [ ] 비교 성능 TC를 일반 SQL/shell/medium CI 및 기본 PR CI의 자동 실행 선택에 추가하지 않는다. 성능 판정은 승인된 별도 performance 실행 경로에서 수행한다.

기능·저장 공간 TC는 [CBRD-26659](https://jira.cubrid.org/browse/CBRD-26659)에서 TC 저장소의 직접 검증·리뷰·승인·병합으로 관리한다. 그 결과와 본 이슈의 성능 TC 승인·편입은 각각의 범위로 확인한다.

## Definition of done

1·3번의 CRUD 비교 결과와 확인된 성능 저하의 원인·개선 결과를 검토한다. 합의한 성능 및 정확성 기준의 충족 여부를 기록하고, 조사하지 않은 조건은 남은 범위로 명시한다.

성능 regression TC는 본 이슈의 시나리오·판정 기준 승인 기록, 승인 조건의 비교 결과와 원시 자료, performance TC PR의 리뷰·승인과 실제 편입·merge commit, 일반 CI 실행 선택에서 제외된 근거까지 확인한다. 개별 성능 수정이나 측정 완료만으로 이 TC 수락·편입을 완료 처리하지 않는다.
