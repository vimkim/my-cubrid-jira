## Description

### 무엇이 문제인가

OOS는 큰 컬럼 값을 행 밖의 파일에 저장하고 행에는 24바이트 참조 정보인 OOS inline stub을 남기는 기능이다. 파티션 테이블에서는 행을 저장할 목적지 heap과 OOS 값을 소유할 heap이 일치해야 한다. [CBRD-27089 / PR #7927](https://github.com/CUBRID/cubrid/pull/7927)은 목적지 선택 뒤 해당 heap의 OOS 파일에 값을 기록하도록 변경하는 작업이다.

이 이슈의 평가 대상은 그때까지 값을 보관하는 메모리 표현이다. [2026-10-07 승인 설계](https://github.com/vimkim/my-cubrid-docs/blob/a082804862d0f3225535253dc048d0c2f6d0e691/cbrd-27089/design/no-record-type-design.md#L15)는 `heap_pending_record` 가 작은 행 버퍼인 compact 행과 선택된 payload를 함께 소유하도록 한다. 행 안의 임시 stub에는 NULL head OOS OID·길이·payload 번호가 들어간다. 목적지 결정 전에 값을 읽는 함수에는 owner를 빌려 전달하고, 목적지가 정해지면 OOS 값을 기록한 뒤 같은 stub 자리를 실제 참조로 바꾼다. 이미 인라인 행을 받는 client copy-area 경로는 목적지를 먼저 선택하고 필요한 변환을 수행한다.

[2026-10-12 리뷰 제안](https://github.com/CUBRID/cubrid/pull/7927#discussion_r4246448112)은 큰 값도 전체 인라인 행 안에 유지하면서 목적지 선택과 키 평가에 일반 reader를 사용하고, 이후 직렬화된 바이트를 OOS로 분리하자는 대안이다. owner 전달과 일부 `DB_VALUE` 왕복 재인코딩을 줄일 가능성이 있다. 현재 방식도 목적지 선택 뒤 OOS를 기록하므로, 비교할 차이는 목적지 선택 전의 표현과 최종 분리 위치이다.

현재 부족한 것은 **같은 지원 범위에서 이 대안을 적용할 수 있는지, 복잡성 감소가 새로 생기는 비용과 예외를 상쇄하는지 판단할 근거**이다. 기존 전체 인라인 POC는 일부 경로에서 가능성을 보였으나 전체 대체안으로 채택하지 않고 철회하였다. 따라서 미검토 상태에서 처음 시작하는 과제도, 이미 채택한 설계를 구현하는 과제도 아니다.

### 왜 문제인가

현재 설계에서 파티션 키·중복 키·인덱스 관련 값을 읽는 개발자는 일반 행 바이트뿐 아니라 해당 owner의 수명과 준비 상태도 고려해야 한다. 입력 경로를 추가하거나 수정할 때 owner 전달, queue에 보관한 행의 수명, 실패 후 정리까지 함께 검토해야 하는 구체적인 유지보수 부담이 있다. 일부 client copy-area·재분배 입력은 변환 과정에서 디코딩과 재인코딩도 수행한다. 다만 이 부담으로 발생한 장애 빈도나 개발 시간은 측정하지 않았다.

전체 인라인 대안이 이 부담을 줄일 수 있더라도, 동기 SQL 호출에서 짧게 빌린 속성 정보만으로 loader queue의 긴 수명을 처리할 수 있다고 볼 수는 없다. 이미 OOS 참조를 가진 복제 입력, 실제 기록 전에 중복 여부를 탐색하는 REPLACE/ODKU, 재평가 경로도 따로 확인해야 한다. 지원 경로를 줄여 얻은 코드 감소를 전체 설계의 단순화로 계산하면 채택 판단을 잘못할 수 있다.

처리 위치를 옮길 때는 UPDATE의 OOS 생성·인덱스 처리·복제 로그·heap 갱신과 실패 정리의 순서, bulk INSERT의 OOS 처리와 heap 데이터 페이지 latch 순서를 보존해야 한다. 이는 후보를 평가할 때 확인할 위험이며 현재 PR에서 순서 위반을 발견했다는 의미는 아니다. 메모리 역시 payload 총량만 비교하면 큰 연속 버퍼의 확장·복사와 queue의 최대 보관량을 놓칠 수 있다.

### 왜 해결해야 하는가

평가를 미루면 현재 구조의 유지보수 부담을 그대로 받아들여야 하는지, 대안으로 줄일 수 있는지 결정하지 못한 상태가 지속된다. 반대로 기존 POC의 일부 성공만으로 전환하면 미지원 입력 경로와 실패 처리를 뒤늦게 설계하며 변경 비용이 커질 수 있다. 필요한 결과는 구현량 감소라는 인상 대신 적용 가능성·보존할 계약·비용을 근거로 한 결정이다.

현재 승인 설계를 유지하는 것은 가능한 기준안이다. [작은 copy-area 행의 불필요한 변환을 줄인 별도 개선](https://github.com/CUBRID/cubrid/pull/7927#issuecomment-6162441044)도 이미 보고되었다. 그 개선의 성능 수치는 이번 전체 인라인 대안의 효과로 사용하지 않는다. 국소 개선이나 코드 TODO는 후속 검토에 도움이 되지만, 전체 지원 범위의 대체 가능성과 비용 비교를 대신하지는 못한다.

리뷰에서 후속 검토와 추적을 요청했고 기존 POC·철회·승인 기록도 남아 있으므로, 같은 실험을 반복하지 않도록 이 평가에 연결한다. 운영 장애에 따른 긴급성이나 완료 기한은 확인되지 않았다. 현재 설계를 유지하는 결론도 허용하며, 재설계 채택과 후속 구현은 평가 결과에 따라 별도로 결정한다.

## Parent and Scope

부모는 OOS TODO를 추적하는 [CBRD-26978](http://jira.cubrid.org/browse/CBRD-26978)이다. 이 Sub-task의 산출물은 OOS 분리 시점 지연 대안의 적용 가능성과 비용을 비교한 평가 및 채택 여부 결정이다. CBRD-27089와 PR #7927은 비교 배경이며 이 이슈의 부모나 게시 대상이 아니다.

평가에서는 일반 INSERT/UPDATE와 파티션 이동뿐 아니라 client copy-area, 재분배, loader의 batch·행별 fallback, 복제, REPLACE/ODKU 및 재평가 경로를 비교 범위에 포함한다. 각 경로에 대해 현재 지원 상태와 후보의 적용 여부를 구분한다. 현재 미지원인 기능까지 구현 완료를 요구하지 않으며, 지원 범위를 줄이는 후보는 그 차이를 명시한다.

미할당 컬럼의 OOS 체인 재사용을 다루는 CBRD-27230 등 별도 과제를 이 평가에서 구현하는 것으로 확대하지 않는다. 비교는 평가 시점의 승인 요구사항을 기준으로 하며, 기존 구현이나 과거 POC를 요구사항 자체로 취급하지 않는다.

현재 방식은 명시적 owner 전달을 유지하면서 준비한 compact 행을 재사용하고, 대안은 상위 계층 의존성을 줄이는 대신 전체 인라인 행의 수명과 뒤늦은 축소 처리를 부담한다. 같은 지원 범위에서 정합성을 보존하고 단순화 효과가 비용을 감당할 때 대안 채택을 검토한다. 효과가 작거나 특정 경로의 위험·비용이 크면 현재 설계를 유지할 수 있다. payload 총량이나 코드 줄 수만으로 우열을 결정하지 않는다.

## Acceptance Criteria

1. 현재 승인 설계와 대안을 같은 지원 범위로 비교하고, 경로별 확인 결과·제외 범위·미확인 사항을 명시한다.
2. UPDATE와 bulk INSERT의 순서, 값·소유권·실패 정리, loader·복제·중복 키·재평가 경로의 적용 가능성에 대해 근거 있는 판정을 남긴다.
3. 복잡성·재인코딩·연속 버퍼 비용·최대 queue 메모리·성능을 비교한다. 실행 측정과 소스 추론을 구분하고, 미측정 항목이 결론에 주는 한계를 밝힌다. 성능 우위나 특정 개선율을 미리 요구하지 않는다.
4. 채택·현행 유지·조건부 보류 중 하나의 결론과 이유를 남긴다. 보류이면 남은 판별 조건과 후속 작업을 특정한다. 평가 이슈는 제품 수정 없이도 완료할 수 있다.

## Definition of done

분석 보고서에 비교 소스의 전체 commit, 지원 범위 표, 경로별 정합성 근거, 비용 비교와 최종 판단을 남긴다. 새 실험을 수행하면 OS·빌드 설정·입력 데이터·실행 명령·원시 결과를 함께 보관하여 다른 개발자가 재현할 수 있게 한다. 테스트 결과는 해당 revision과 실행 범위에만 귀속한다.

분석 결과의 의사결정에 필요한 증거가 충분한지 검토하고, 남은 불확실성의 처리와 후속 구현 여부를 기록한다. 상세 측정 시나리오·허용 비용·최종 검증 범위는 ANALYSIS 산출물로 확정한다.
