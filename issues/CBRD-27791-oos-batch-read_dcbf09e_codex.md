## Description

### 무엇이 문제인가

OOS(Out-of-row Overflow Storage)는 큰 컬럼 값을 행 밖에 따로 저장하고, 행에는 그 위치를 가리키는 참조를 남기는 방식이다. 작은 컬럼만 조회하면 큰 값을 가져올 필요가 없어 빨라질 수 있다.

큰 컬럼의 내용까지 필요한 조회는 다음 동작을 반복한다.

1. 행의 기본 저장 공간인 heap에서 다음 행을 읽는다.
2. 그 행에 있는 참조를 따라, 조건 비교나 집계에 필요한 큰 값을 가져온다.
3. 다음 행으로 넘어가 같은 일을 반복한다.

문제는 이처럼 큰 값까지 가져오는 조회가 OOS 적용 전보다 느려진 경우가 있다는 것이다. 이번 실험에서는 큰 컬럼 하나의 내용을 비교하는 쿼리의 실행 시간이 약 2.4배로 늘었다.

### 왜 문제인가

큰 컬럼에 특정 내용이 들어 있는 행을 세거나 여러 큰 값의 내용을 집계하려면, 사용자는 실제 값을 읽는 비용을 피할 수 없다. 작은 컬럼 조회가 빨라져도 이 작업에서는 결과를 더 오래 기다릴 수 있다.

같은 100,000행을 대상으로 **실제 엔진에서 SQL을 실행한 결과**는 다음과 같다. 기준 엔진은 OOS 적용 전 비교 대상이고, 이 입력에서는 큰 행을 저장하기 위해 기존 overflow 저장을 사용한다.

| 조회하는 내용 | 기준 엔진 | OOS 엔진 |
| --- | ---: | ---: |
| 작은 컬럼만 집계 | 1.88초 | 0.82초 |
| 큰 컬럼 하나의 전체 내용 비교 | 2.38초 | 5.72초 |
| 모든 컬럼의 내용을 읽어 집계 | 3.46초 | 4.12초 |

위 수치는 작업 전용 DB 파일의 OS 캐시 해제를 요청한 뒤 측정한 3회 중앙값이다. 운영체제가 메모리에 보관한 파일 내용을 재사용하기 어려운 조건을 조사했다. 같은 큰 값 비교 쿼리도 한 번 실행한 뒤 다시 조회하면 기준 1.23초, OOS 1.00초였다. 따라서 성능 저하가 나타나는 캐시·조회 조건의 범위도 함께 확인해야 한다.

### 왜 해결해야 하는가

큰 값 비교 쿼리에서 OOS의 페이지 읽기 횟수와 CPU 시간은 기준 엔진보다 줄었다. 그런데 전체 실행 시간은 늘었다. 이 차이를 설명하기 위해 **읽는 위치와 순서가 대기를 늘렸을 가능성**을 조사했다.

SQL 실행 중 기록한 파일 읽기 요청을 별도 프로그램에서 다시 실행하고, 요청의 순서를 바꿔 비교했다. 이 실험에서는 SQL을 실행하지 않고 파일 읽기만 수행한다.

| 별도 프로그램에서 같은 파일 읽기를 재생한 방법 | 시간 |
| --- | ---: |
| 원래 요청 순서대로 읽기 | 4.413초 |
| 기록을 작은 구간으로 나누고, 각 구간의 OOS 요청을 파일 위치순으로 읽기 | 3.449초 |

읽는 순서를 바꾸면 대기를 줄일 가능성이 있다는 단서다. 다만 실제 엔진에는 여러 행의 참조를 모으고 조회 결과를 만드는 비용이 추가되므로, 이 결과가 실제 SQL의 개선을 보장하지는 않는다.

이 이슈에서 검토할 batch read는 **여러 행에서 필요한 큰 값의 읽기를 조금씩 모아, 읽는 순서나 묶음을 조절하는 방법**이다. 한 번에 모을 범위를 제한하고, 실제 엔진에서 비용을 포함해 비교해야 한다. 작은 컬럼 조회의 이득을 유지하면서 큰 값 조회의 대기도 줄이는 것이 목표다.

운영체제의 미리 읽기를 끄는 설정(`data_file_os_advise=3`)은 기존 대조에서 양쪽 엔진을 모두 느리게 했다. 이 설정으로 개선되지 않아, 읽기 방식 자체를 검토한다.

## Specification Changes

큰 값 조회의 읽기 대기를 줄이면서 다음 동작을 유지한다.

- 작은 컬럼만 필요하거나 앞선 조건에서 결과가 정해진 경우, 불필요한 큰 값을 가져오지 않는다.
- 조회 시점에 맞는 행 버전의 값을 읽고, 참조한 저장 위치가 여전히 같은 값을 가리키는지 확인한다.
- 읽기 순서를 바꿔도 동시 접근 제어와 결과 데이터의 수명을 유지한다. 실패·취소 시 자원을 정리하고 불완전한 값을 결과로 내보내지 않는다.

한 번에 모을 행·페이지·바이트 수, 메모리 상한, 적용하지 못하는 경우의 처리 방법은 ANALYSIS에서 정한다.

### 파일 읽기 재생의 조건과 한계

앞의 재생 실험은 heap 페이지 읽기 64개를 기준으로 기록을 나눠 각 구간의 OOS 요청 순서를 조정했다. 이는 기록을 나누는 기준이며 실제 행 64개를 뜻하지 않는다. 구간 안에서 읽을 위치는 기록을 통해 미리 안다. 실제 엔진에서 행을 수집하고, 조회 가능한 버전인지 판단하고, 엔진 내부 캐시를 확인하고, 결과를 만드는 비용은 포함하지 않는다.

인접 요청을 합친 경우는 정렬만 한 경우보다 느렸다. 요청 사이의 원래 필요하지 않은 구간까지 함께 읽으면 1.965초로 줄었으나 요청 바이트가 72.4% 늘었다. 따라서 속도와 추가 읽기 비용을 함께 평가해야 한다. 전체 수치와 소스 근거는 [상세 분석](https://github.com/vimkim/my-cubrid-docs/blob/main/CBRD-27791/CBRD-27791-oos-batch-read-analysis_dcbf09e_codex.md)에 있다.
