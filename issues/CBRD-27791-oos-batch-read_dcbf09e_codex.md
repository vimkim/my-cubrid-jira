## Description

### 무엇이 문제인가

OOS(Out-of-row Overflow Storage)는 큰 컬럼 값을 행 밖에 따로 저장하고, 행에는 그 위치를 가리키는 참조를 남기는 방식이다. 작은 컬럼만 조회하면 큰 값을 가져올 필요가 없어 빨라질 수 있다.

큰 컬럼의 내용까지 필요한 조회는 다음 동작을 반복한다.

1. 행의 기본 저장 공간인 heap에서 다음 행을 읽는다.
2. 그 행에 있는 참조를 따라, 조건 비교나 집계에 필요한 큰 값을 가져온다.
3. 다음 행으로 넘어가 같은 일을 반복한다.

문제는 이처럼 큰 값까지 가져오는 조회가 OOS 적용 전보다 느려진 경우가 있다는 것이다. 이번 실험에서는 큰 컬럼 하나의 내용을 비교하는 쿼리의 실행 시간이 약 2.4배로 늘었다.

### 왜 문제인가

큰 컬럼에 특정 내용이 들어 있는 행을 세거나 여러 큰 값의 내용을 집계하려면, 사용자는 실제 값을 읽는 비용을 피할 수 없다. 작은 컬럼 조회가 빨라져도 이 작업에서는 결과를 더 오래 기다릴 수 있다.

같은 100,000행을 대상으로 **실제 엔진에서 SQL을 실행한 결과**는 다음과 같다. 기준 엔진은 OOS 적용 전 비교 대상이고, 이 입력에서는 큰 행을 저장하기 위해 기존 overflow 저장을 사용한다.

| 조회하는 내용 | 기준 엔진 | OOS 엔진 |
| --- | ---: | ---: |
| 작은 컬럼만 집계 | 1.88초 | 0.82초 |
| 큰 컬럼 하나의 전체 내용 비교 | 2.38초 | 5.72초 |
| 모든 컬럼의 내용을 읽어 집계 | 3.46초 | 4.12초 |

위 수치는 테스트 DB의 데이터 파일에 대해 OS 캐시 해제를 요청하고, 남은 캐시가 0B임을 확인한 뒤 서버를 시작해 측정한 3회 중앙값이다. 일반 사용자 권한으로 파일별 캐시 해제를 요청했다. 구체적인 절차는 아래 측정 근거에 설명한다.

같은 큰 값 비교 쿼리도 한 번 실행한 뒤 다시 조회하면 기준 1.23초, OOS 1.00초였다. 따라서 성능 저하가 나타나는 캐시·조회 조건의 범위도 함께 확인해야 한다.

### 왜 해결해야 하는가

큰 값 비교 쿼리에서 OOS의 페이지 읽기 횟수와 CPU 시간은 기준 엔진보다 줄었다. 그런데 전체 실행 시간은 늘었다. 이 차이를 설명하기 위해 **읽는 위치와 순서가 대기를 늘렸을 가능성**을 조사했다.

SQL 실행 중 기록한 파일 읽기 요청을 별도 프로그램에서 다시 실행하고, 요청의 순서를 바꿔 비교했다. 이 실험에서는 SQL을 실행하지 않고 파일 읽기만 수행한다.

| 별도 프로그램에서 같은 파일 읽기를 재생한 방법 | 시간 |
| --- | ---: |
| 원래 요청 순서대로 읽기 | 4.413초 |
| 읽기 요청을 일정 범위씩 모아, 큰 값이 저장된 파일 위치 순서대로 읽기 | 3.449초 |

읽는 순서를 바꾸면 대기를 줄일 가능성이 있다는 단서다. 다만 실제 엔진에는 여러 행의 참조를 모으고 조회 결과를 만드는 비용이 추가되므로, 이 결과가 실제 SQL의 개선을 보장하지는 않는다.

이 이슈의 개선 대상인 **읽기 지역성**은 함께 읽을 데이터를 파일 안의 가까운 위치순으로 방문하는 성질이다. 개선 후보인 batch read는 **먼저 몇 개 행을 읽어 필요한 큰 값의 위치를 모은 뒤, 그 값들을 읽는 순서나 한 번에 읽을 범위를 조절하는 방법**이다. 작은 컬럼 조회의 이득을 유지하면서 큰 값 조회의 대기도 줄이는 것이 목표다.

### batch read는 무엇을 바꾸는가

문서 테이블에 `id`와 큰 `본문` 컬럼이 있고, 세 문서의 본문이 모두 필요한 조회를 가정한다. 행에는 본문을 찾을 참조가 있으며, 본문은 같은 데이터 파일의 다음 위치에 저장돼 있다고 하자. 페이지 번호와 세 행이라는 크기는 설명을 위한 예시다.

| 행을 발견하는 순서 | 행에 기록된 본문 위치 |
| --- | --- |
| 1번 문서 | 파일의 103번 페이지 |
| 2번 문서 | 파일의 101번 페이지 |
| 3번 문서 | 파일의 102번 페이지 |

현재처럼 한 행씩 처리하면 행에서 본문 위치를 알아내는 즉시 본문을 가져온다.

```text
1번 행 읽기 → 103번 페이지에서 본문 가져오기
2번 행 읽기 → 101번 페이지에서 본문 가져오기
3번 행 읽기 → 102번 페이지에서 본문 가져오기
```

batch read 후보에서는 본문을 가져오기 전에 몇 개 행의 위치를 모아둔다.

1. 세 행을 먼저 읽어 `1번 문서 → 103`, `2번 문서 → 101`, `3번 문서 → 102`라는 목록을 만든다.
2. 본문은 파일 위치순으로 `101 → 102 → 103`에서 가져온다.
3. 가져온 본문을 각각 2번·3번·1번 문서에 연결한다.

여기서 **읽는 순서 조절**은 `103 → 101 → 102`를 `101 → 102 → 103`으로 바꾸는 것이다. **묶음 조절**은 바로 이어진 101·102·103번 페이지를 각각 읽을지, 한 번의 요청으로 함께 읽을지 검토한다는 뜻이다.

**조금씩 모은다**는 예를 들어 세 행을 처리한 뒤 다음 세 행을 모으는 방식이다. 실제로 몇 행을 모을지, 순서만 바꿀지, 여러 페이지를 한 번에 읽을지와 적용할 조회는 ANALYSIS에서 결정한다.

### 왜 성능 향상에 도움이 될 가능성이 있는가

같은 양의 데이터를 읽어도 요청의 순서에 따라 데이터를 기다리는 시간이 달라질 수 있다. 위 예시에서는 큰 값을 `101 → 102 → 103`으로 읽을 때 파일의 가까운 위치를 차례로 방문한다.

도움이 될 수 있는 한 가지 경로는 운영체제의 미리 읽기다. 101번 페이지를 읽으면서 운영체제가 102·103번 페이지도 미리 읽어두었다면, 뒤의 두 요청은 OS 캐시에 있는 데이터를 이용할 수 있다. 이는 가능한 동작을 설명하는 예시이며, 이번 측정에서 미리 읽기의 기여분을 따로 확인한 결과는 아니다.

이번에 개선 가능성이 있다고 판단한 직접 근거는 **읽을 파일 위치와 요청 횟수·요청 바이트 수를 유지하고 순서를 바꾼 재생 실험에서 4.413초가 3.449초로 약 21.8% 줄었다는 것**이다. 이 조건에서 읽기 순서가 시간에 영향을 준다는 근거다. 미리 읽기, 저장 장치 내부 캐시와 요청 처리 방식이 각각 얼마나 기여했는지는 분리하지 못했다.

여러 페이지를 한 번의 요청으로 읽으면 요청 횟수를 줄일 수 있지만, 시간까지 줄어드는지는 별도로 확인해야 한다. 실제 재생에서 인접 요청을 합친 경우는 3.974초로, 순서만 바꾼 3.449초보다 느렸다. 따라서 순서 조절과 요청 병합은 효과를 따로 평가한다.

실제 엔진에서는 행과 참조를 모으는 비용까지 포함해 SQL 성능을 검증해야 한다. 위 예시와 재생 결과를 바탕으로 시제품을 검토하며, 최종 적용 방식은 그 검증 결과로 정한다.

## Specification Changes

큰 값 조회의 읽기 대기를 줄이면서 다음 동작을 유지한다.

- 작은 컬럼만 필요하거나 앞선 조건에서 결과가 정해진 경우, 불필요한 큰 값을 가져오지 않는다.

- 읽기 순서를 바꿔도 동시 접근 제어와 결과 데이터의 수명을 유지한다. 실패·취소 시 자원을 정리하고 불완전한 값을 결과로 내보내지 않는다.

### 각 층의 책임과 현재 구현

필요한 행·속성과 참조를 모으는 범위는 scan에서, 값을 읽고 원래 요청에 연결하는 처리는 OOS에서 검토한다. 캐시 재사용과 동시에 같은 페이지를 읽는 경우, 수정된 페이지와 복구·암호화 처리는 페이지 버퍼의 기존 동작을 보존한다. 파일을 직접 크게 읽는 호출로 이 경로를 우회하지 않는다.

현재 `heap_oos_read_grouped_payloads`와 `oos_read_many`는 한 행의 여러 OOS 컬럼을 처리하고 같은 시작 페이지의 중복 확보를 줄이는 기능이다. 여러 행의 읽기를 모아 순서를 조절하려면 별도 설계가 필요하다. 함수별 동작과 세부 제약은 [구현·검증 계획](https://github.com/vimkim/my-cubrid-docs/blob/main/CBRD-27791/CBRD-27791-oos-batch-read-plan_dcbf09e_codex.md)에 정리돼 있다.

### 저장 시점의 배치 정책 변경은 별도 후속 범위

관련 OOS 값을 저장할 때부터 가까운 페이지에 배치하거나, 기존 값을 재배치하는 정책은 본 이슈의 구현 범위에 포함하지 않는다. 이는 페이지 할당·빈 공간 재사용·UPDATE·복구까지 영향을 줄 수 있으므로, 추진할 경우 별도 후속 이슈에서 분석한다. 현재는 저장 배치를 바꾸지 않고 읽는 순서와 요청 방식을 개선하는 후보를 검토한다.

### OS 캐시 해제와 미리 읽기 설정

파일별 OS 캐시 해제는 다음 순서로 수행했다.

1. 테스트 DB 서버를 정지한다.
2. 실행 사용자가 소유한 테스트 DB의 데이터 파일을 열고 `fsync`로 아직 기록하지 않은 내용을 디스크에 반영한다.
3. `POSIX_FADV_DONTNEED`로 해당 파일 내용을 OS 캐시에서 버리도록 요청한다. 파일을 열 수 있는 일반 사용자 권한으로 호출할 수 있다.
4. `fincore`로 대상 파일 내용이 메모리에 얼마나 남아 있는지 확인하고, 그 뒤 서버를 시작한다.

앞의 큰 값 비교 쿼리를 측정한 기준 엔진 3회와 OOS 엔진 3회에서 모두, 서버 시작 전 대상 데이터 파일의 캐시 합계가 0B였다. 대상은 기준 엔진의 데이터 파일 11개와 OOS 엔진의 데이터 파일 13개다. 첫 기준 엔진 측정에서는 해제 요청 전 3,278,258,176B였고 요청 후 0B였다. 전역 OS 캐시와 저장 장치 내부 캐시는 초기화하지 않았다.

`data_file_os_advise=3`은 이 캐시 해제와 별개의 설정이다. [설정 적용 코드](https://github.com/CUBRID/cubrid/blob/dcbf09e4f7fd02ff9c8fc6493ec8887fc2919d67/src/storage/file_io.c#L3033)에서는 `POSIX_FADV_RANDOM`으로 전달돼, 앞으로 파일 내용을 미리 읽는 기능을 끈다. 기존 SQL 대조는 파일별 캐시 해제를 수행한 뒤 이 설정을 바꿔 비교했으며, 두 엔진 모두 느려졌다. 설정별 수치는 [앞선 읽기 진단](https://github.com/vimkim/my-cubrid-docs/blob/main/CBRD-27788/CBRD-27788-oos-cold-read-diagnosis_dcbf09e_codex.md)에 있다. 두 기능의 의미는 [Linux 매뉴얼](https://man7.org/linux/man-pages/man2/posix_fadvise.2.html)에서 확인할 수 있다.

### 파일 읽기 재생의 조건과 한계

앞의 재생 실험은 heap 페이지 읽기 64개를 기준으로 요청 목록을 나눴다. 각 묶음에서 OOS 이외의 요청을 원래 순서대로 먼저 읽고, OOS 요청을 파일 위치순으로 읽었다. 이는 목록을 나누는 기준이며 실제 행 64개를 뜻하지 않는다. 묶음 안에서 읽을 위치는 기록을 통해 미리 안다. 실제 엔진에서 행을 수집하고, 조회 가능한 버전인지 판단하고, 엔진 내부 캐시를 확인하고, 결과를 만드는 비용은 포함하지 않는다.

인접 요청을 합친 경우는 정렬만 한 경우보다 느렸다. 요청 사이의 원래 필요하지 않은 구간까지 함께 읽으면 1.965초로 줄었으나 요청 바이트가 72.4% 늘었다. 따라서 속도와 추가 읽기 비용을 함께 평가해야 한다. 전체 수치와 소스 근거는 [상세 분석](https://github.com/vimkim/my-cubrid-docs/blob/main/CBRD-27791/CBRD-27791-oos-batch-read-analysis_dcbf09e_codex.md)에 있다.

## Repro

두 revision의 독립 설치·DB를 준비하고, 각각의 CSQL로 [동일 입력](https://github.com/vimkim/my-cubrid-docs/blob/main/CBRD-27791/fixture.sql)을 적재한다. 위 설정을 적용한 새 DB를 사용한다.

```sh
csql -C -u dba -i fixture.sql <database>
```

큰 컬럼 하나의 전체 내용을 비교한 쿼리는 다음과 같다. 정답은 100,000이다.

```sql
SELECT /*+ NO_MERGE RECOMPILE PARALLEL(0) NO_PARALLEL_HEAP_SCAN */ COUNT(*)
FROM perf_overflow_22000
WHERE cold_1 = CAST(REPEAT(X'AA', 7000) AS BIT VARYING);
```

위 SQL을 `q4.sql`로 저장한 뒤 각 설치에 맞는 `csql -C -u dba -i q4.sql <database>`로 실행한다.

캐시 조건은 위의 파일별 OS 캐시 해제 절차로 준비한다. DB 재시작만으로는 OS 캐시가 남을 수 있다. 전체 준비 절차와 물리 배치에 따른 재현 한계는 상세 분석의 재현 절차에 있다.
