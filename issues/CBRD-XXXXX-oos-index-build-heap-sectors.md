# [OOS] 인덱스 생성 정렬이 heap 섹터만 세어, 값이 OOS로 옮겨진 테이블에서 병합 fan-in과 병렬도가 낮아진다

**한 줄 요약**: OOS 브랜치의 shell 테스트 `cbrd_27236_merge` 실패를 분석하다가, 인덱스 생성 정렬이 병합 fan-in(CBRD-27236)과 병렬 작업자 수를 heap 파일의 섹터 수로만 정하는 것을 확인했다. 컬럼 값이 OOS 파일로 옮겨지면 정렬할 키의 양은 그대로인데 heap만 작아져, 병합 횟수가 늘고 병렬 생성이 직렬로 바뀐다. 이 판단 기준을 OOS에서 어떻게 할지 정해야 한다.

## Issue Triage

**이슈 수행 목적**: OOS로 값이 옮겨진 테이블에서도 인덱스 생성의 병합 fan-in과 병렬도가, 정렬할 데이터의 양에 맞게 정해지게 한다.

**이슈 수행 이유**: `btsort_get_num_data_sectors`(`src/storage/btree_sort.c`)는 fan-in 상한을 정할 때 heap 파일의 데이터 섹터만 센다. `btsort_check_parallelism`도 heap의 페이지와 섹터로 병렬도를 정하고, 섹터 수가 병렬도보다 적으면 직렬로 돌아간다. OOS는 4,060바이트(16K 페이지 기준 inline target)를 넘는 행에서 큰 가변 컬럼부터 OOS 파일로 옮기고 heap에는 작은 참조만 남긴다. 그래서 heap 섹터 수가 정렬 데이터의 양을 나타내지 못한다. feature/oos-merge `30292700ac` debug 빌드에서 측정으로 확인했다.

**영향**: 큰 가변 컬럼이 있는 테이블에 인덱스를 만드는 사용자와 운영자가 영향을 받는다. 인덱스할 컬럼이 OOS로 옮겨지는 경우 아래 측정에서 직렬 생성은 병합이 2회에서 8회로 늘었고, 병렬 생성은 작업자 8개 대신 1개로 돌았다. 각 조건 1회 실행한 debug 빌드 값이라 방향만 보여준다. 인덱스 내용은 develop과 같아 정확성 문제는 아니다. release 빌드, 실제 업무 규모의 테이블, 다른 페이지 크기에서는 측정하지 않았다.

## Description

인덱스 생성 정렬은 두 곳에서 heap의 크기를 정렬 데이터 양의 대리 값으로 쓴다.

- **병합 fan-in**: CBRD-27236은 정렬 run을 합칠 때 한 번에 여는 run 수(fan-in)를 정렬 버퍼와 데이터 섹터 수로 제한한다. `btsort_get_num_data_sectors`는 각 클래스의 `hfids[i].vfid`, 즉 heap 파일만 센다.
- **병렬 분할**: `btsort_check_parallelism`은 `hfids[0]` heap의 페이지와 섹터로 병렬도를 계산하고, `n_sects < parallel_num`이면 1을 돌려준다. 이 검사는 CBRD-27236보다 먼저 있었다.

develop에서는 행이 heap에 그대로 있으므로 heap 섹터 수가 데이터 양과 비례한다. OOS에서는 그 비례가 깨진다. 아래 두 측정 모두 OOS가 정렬하는 키의 개수와 크기는 develop과 같았다.

### 측정 1: 인덱스 컬럼이 OOS로 옮겨지는 테이블

`tv (id int not null, v varchar(4100) collate utf8_bin)`에 약 4,100바이트 값 27,000행을 넣고 `create index i_v on tv (v)`를 실행했다. 정렬 버퍼는 `index_build_buffer_size=512K`, 병렬 생성은 `index_build_parallelism=8`, `parallel_index_build_page_threshold=16`으로 설정했다.

| | develop `785021e` debug | OOS `30292700ac` debug |
|---|---|---|
| heap | 9,001 페이지, 평균 레코드 4,129바이트 | 105 페이지(2 섹터), 평균 레코드 49바이트 |
| 직렬 생성 | run 222개, fan-in 16 후 14, 병합 2회, 14.1초 | run 222개, fan-in 2, 병합 8회, 21.2초 |
| 병렬 생성 설정 | 작업자 8개, 작업자 fan-in 16, 5.6초 | 작업자 1개(직렬), 병합 8회, 12.2초 |

OOS에서는 `v`가 OOS 파일로 옮겨져 heap에 참조만 남는다. 정렬은 약 110 MB의 키를 읽는데, fan-in 상한은 heap 2섹터를 기준으로 최소값 2까지 떨어진다.

### 측정 2: 인덱스 컬럼은 heap에 남고 다른 컬럼이 옮겨지는 테이블

shell 테스트 `cbrd_27236_merge`의 `tw` 테이블(키 1,799자, 정렬하지 않는 pad 2,304자, 행 4,151바이트)이다. OOS에서는 pad가 OOS 파일로 옮겨진다.

| | develop | OOS |
|---|---|---|
| heap 데이터 섹터 | 141 | 61(OOS 파일 71섹터 별도) |
| 작업자 8개의 fan-in | 16 | 7 |
| 정렬 입력 | 27,000건, 512K에서 run 100~101개 | 동일 |

이 차이로 테스트의 4, 5번 검사가 다른 병합 경로를 탔다. 테스트는 pad를 줄여 행이 inline target 안에 머물게 하는 방식으로 따로 고쳤다. 이 이슈는 엔진의 판단 기준만 다룬다.

### ANALYSIS에서 정할 사항

- fan-in과 병렬도의 기준을 무엇으로 할지 정한다. 후보는 heap 섹터에 해당 heap의 OOS 파일 섹터를 더하는 것, 또는 정렬 입력의 실제 크기(키 수와 키 크기)를 쓰는 것이다. 측정 2의 원래 데이터에 OOS 섹터를 더하면 작업자당 (61 + 71) / 8 = 16이 되어 develop과 같아진다고 추정하지만 구현해 측정하지는 않았다.
- OOS 파일 섹터를 더하면, 인덱스 컬럼이 아닌 값만 OOS에 있는 테이블에서는 정렬 데이터보다 큰 값이 기준이 된다. 이 과대 추정이 문제 되는지 확인한다.
- 병렬 분할은 heap 섹터를 작업자에게 나누는 구조라서, 섹터가 2개인 heap은 기준 값을 바꿔도 작업자 8개에 일을 나눌 수 없다. 병렬 분할까지 바꿀지, fan-in만 바꿀지 범위를 정한다.
- release 빌드와 더 큰 테이블에서 실제 시간 차이를 측정한다.

### 관련 이슈

- CBRD-27236: 인덱스 생성 정렬의 fan-in을 정렬 버퍼로 정하는 변경.
- CBRD-28055: 같은 원인의 develop 쪽 문제다. 페이지보다 긴 레코드는 heap의 오버플로 파일에 저장되는데 섹터를 heap 파일에서만 세어 fan-in이 2~3으로 떨어진다. 오버플로 파일 섹터를 더하는 방향으로 고칠 예정이며, 수락 조건에 shell `cbrd_27236_merge`의 수치 갱신이 들어 있다. 이 이슈는 그 대상에 OOS 파일을 넣을지를 다룬다.
- CBRD-26357: OOS.
