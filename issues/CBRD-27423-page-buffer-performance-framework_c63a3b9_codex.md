### 1. 실제 구현을 사용하는 실행기

서버 빌드의 페이지 버퍼를 실제로 초기화하고, 필요한 데이터와 페이지를 준비한 뒤 fix/unfix를 호출하는 실행기를 제안한다. 파일·디스크·로그·DWB와 데몬은 선택한 시나리오에 필요한 실제 경로를 사용한다. 단순 모형이나 mock 결과를 엔진 성능으로 취급하지 않는다.

실행기는 준비, warm-up, 측정, 미완료 작업 확인, 정리 단계를 구분한다. 빌드와 데이터 생성 시간은 측정 구간에서 제외한다. 비동기 작업은 측정 종료 때 남아 있는 작업량과 후속 처리 시간을 기록하여, 측정 구간 밖으로 미룬 비용이 성능 개선으로 보이지 않게 한다.

실행 단위마다 전용 데이터 디렉터리와 인스턴스를 사용한다. 준비 실패나 시간 초과 시에도 종료 코드, 로그, 완료된 작업량을 보관하고 다른 실행의 상태를 재사용하지 않는다. 빌드와 재현 절차는 CMake 및 저장소에 포함되는 실행 스크립트로 제공한다. 실행기 위치와 엔진 초기화 연결 방식은 조사 후 결정한다.

성능 수치는 최적화된 빌드로 수집하고, assertion과 상세 추적을 위한 실행은 별도로 둔다. 상세 이벤트 기록과 프로파일링은 관측 비용을 만들므로 기본 시간 측정과 분리하고, 계측을 끈 대조 실행으로 영향을 확인한다.

엔진 버퍼의 cold/warm 상태와 OS 페이지 캐시 상태는 구분한다. 엔진 버퍼 미스나 read 호출을 실제 저장 장치 I/O와 동일시하지 않는다. 저장 장치까지 cold인 조건을 확보하지 못하면 그 한계를 표시하며, 다른 작업에 영향을 주는 시스템 전체 캐시 제거를 기본 절차로 삼지 않는다.

실행별 환경·설정·소스 정보를 담는 manifest, 원시 결과, 로그, 요약 결과와 기준판 대비 변화율을 보관한다. 반복 실행별 값과 중앙값·분산 또는 불확실성 구간을 함께 제시하고, 실패한 실행을 조용히 제외하지 않는다. 시간 초과, 결과 불일치, 실행 조건 불일치는 성능 개선 판정과 분리한다.

같은 빌드를 두 집단으로 나누어 비교하는 A/A 실행으로 측정 편차를 확인한다. 통제된 지연 또는 부하 증가를 넣은 검증용 변경이 보고서에 악화로 나타나는지도 확인한다. 회귀 임계값은 이 편차와 업무상 의미 있는 변화 크기를 기준으로 선정하며, 근거 없이 모든 시나리오에 같은 5% 기준을 적용하지 않는다.

일일 CI를 도입하면 마지막 유효 기준판과 비교하여 회귀 의심 결과 및 재현 명령을 제공한다. 여러 PR이 포함된 revision 차이는 그 자체로 특정 PR의 원인 증명이 아니다. 동일 조건의 재실행과 필요 시 중간 커밋 비교를 거친 뒤 원인을 좁힌다. 실행 주기, 기준판 갱신, 알림 대상과 보관 기간은 후속 결정 사항이다.

### 6. 기록·재생 방식의 조사

SQL 실행 중 VPID, fetch mode, latch mode와 fix/unfix를 기록하여 다른 모듈의 작업 없이 재생하는 방안을 확장 후보로 둔다. 다만 VPID와 호출 순서만으로 원래 실행을 복원할 수는 없다. 페이지 내용, dirty/WAL 상태, 할당·해제, 중첩 소유권, 조건부 fix 실패, 다중 스레드 동기화와 요청 간 간격이 결과에 영향을 준다.

먼저 정해진 데이터 이미지에 대한 읽기 중심 부하에서 재생 가능성을 검증한다. 기록 시작 시 이미 보유한 페이지와 종료 시 미해제 페이지의 처리도 정의한다. 원래 호출 간 시간 간격을 유지할지, 가능한 속도로 재생할지에 따라 측정 질문이 달라지므로 두 방식을 구분한다. 계측이 원래 실행에 주는 영향과 재생의 논리 작업 일치 여부를 확인하기 전에는 SQL 성능을 대표한다고 주장하지 않는다.

### 7. 단계별 결과물

1. 시나리오·지표·실행 조건·비교 가능성 기준과 최소 엔진 구동 방식을 확정한다.
2. 대표 직접 부하로 기준판·변경판 실행 및 비교 보고서 생성을 구현하고 A/A 및 통제된 악화 검증을 수행한다.
3. holder, 경합, 교체, dirty/flush와 혼합 세션으로 범위를 확장하고 대표 SQL 부하로 회귀를 확인한다.
4. 실행 시간과 안정성을 확인한 뒤 일일 CI 및 기록·재생의 도입 여부를 결정한다.

## Acceptance Criteria

아래는 초안의 제안 기준이며, Survey 단계에서 초기 구현 범위를 확정할 때 조정한다.

- [ ] 기준판과 변경판의 revision 및 시나리오를 지정하여 준비부터 비교 보고서까지 재현할 수 있다.
- [ ] 실제 페이지 버퍼 구현을 구동하며, 초기 지원 시나리오와 미지원 범위가 명시되어 있다.
- [ ] 상주 페이지, holder 깊이, 공유 페이지 경합, 교체 압력, dirty/flush를 구분해 측정할 수 있다. 채택하지 않은 후보는 사유와 후속 범위를 남긴다.
- [ ] 동일 빌드 A/A 반복 실행으로 편차를 제시하고, 통제된 악화가 비교 결과에 드러나는 것을 확인한다.
- [ ] foreground 개선과 데몬·I/O·버퍼 미스 증가를 함께 판단할 수 있다. 비동기 작업의 잔여량과 후속 비용을 누락하지 않는다.
- [ ] 전체 SHA, 빌드, 데이터, 설정, harness, 반복별 원시 결과와 종료 상태를 보고서에서 추적할 수 있다.
- [ ] 실패·시간 초과·결과 불일치·계측 불가를 정상 표본이나 0 값으로 처리하지 않는다.
- [ ] 대표 SQL 부하의 결과와 성능을 함께 확인하며, 직접 부하만으로 전체 SQL 성능 개선을 단정하지 않는다.
- [ ] 지원 환경에서 다른 개발자가 문서와 저장소의 스크립트만으로 실행을 재현할 수 있다.

## Definition of done

- [ ] Survey 결과로 초기 구현 범위, 지표 정의, 반복·비교 방식과 결과 형식이 합의되어 있다.
- [ ] 합의한 범위의 실행기, 비교 도구, 대표 시나리오와 재현 문서가 저장소에 포함되어 있다. 구현을 별도 이슈로 분리하면 그 연결과 본 이슈의 종료 범위를 명시한다.
- [ ] 합의한 Acceptance Criteria의 검증 결과와 원시 자료가 보관되어 있다.
- [ ] 결과 검증과 필요한 QA를 통과하고, 반복 실행 후 인스턴스와 데이터 정리 동작을 확인한다.
- [ ] 일일 CI, 기록·재생, 추가 시나리오의 후속 범위와 미결정 사항이 남아 있다면 명시한다.
