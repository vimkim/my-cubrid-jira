예를 들어 적용 조건을 생략한 금지 규칙을 충실히 따르는 에이전트는 실제 코드가 허용하는 수정까지 피할 수 있다. 개발자는 필요한 예외를 매번 설명하거나 우회한 구현을 다시 고쳐야 한다. 프로젝트의 지식을 전달하려고 둔 문서가 오히려 정상적인 개발을 제한하는 상황이다.

이번 작업에서는 현재 모델의 분석 능력을 이용해 지침을 한 줄씩 실제 근거와 대조한다. 더 새 모델이 썼다는 이유만으로 정확하다고 간주하지 않고, 필요한 규칙의 적용 범위와 예외까지 검토해야 같은 문제가 반복되지 않는다.

### 소스 지침의 구성 제안

1. **빌드 경계**: `SERVER_MODE`는 서버, `SA_MODE`는 독립 실행, `CS_MODE`는 클라이언트 라이브러리 빌드임을 설명한다. 디렉터리 이름만으로 판단하지 않고 실제 소스 목록과 전처리 조건을 확인하도록 한다.
2. **자원과 오류 처리**: 할당·해제 API, 소유권, 정리 경로를 함께 검토하도록 한다. 예외 처리와 RAII(객체 수명에 따른 자원 정리)의 적용 범위는 기존 모듈 관례와 대조하며 일괄 금지로 대신하지 않는다.
3. **편집과 포맷팅**: GNU indent 대상 파일에서 씨플러스플러스 구문을 보호하는 방법과 실제 포맷 검사 스크립트를 안내한다. 파일 크기만을 이유로 분리하거나 관계없는 서식을 바꾸지 않도록 한다.
4. **변경 영향 확인**: XASL(질의 실행 계획 구조)의 변경은 생성·직렬화·역직렬화·실행 경로를 함께 살핀다. 저장소나 트랜잭션 변경은 관련 잠금·복구·정리 경로를 확인하도록 해당 모듈 지침에 연결한다.

기존 의존 관계 그림은 함수 호출 흐름과 헤더 의존 관계를 혼동하지 않도록 점검한다. 실제 작업에 도움이 되는 관계만 남기고, 이를 모든 의존성을 나열한 목록으로 취급하지 않는다.
