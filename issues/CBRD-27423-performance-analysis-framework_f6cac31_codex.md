본 이슈는 [CBRD-27193](https://jira.cubrid.org/browse/CBRD-27193)의 하위 조사 과제이며, 기존 요청의 핵심은 실제 페이지 버퍼를 사용하는 기준판과 변경판을 같은 조건에서 비교하는 능력이다. 부하 실행·수집·비교 결과를 연결하여 다른 개발자도 재현할 수 있어야 한다. 도구 선택, 실행기 위치, 초기 시나리오, 수치 기준과 CI 연동은 아직 정해진 구현으로 취급하지 않는다.

페이지 버퍼는 디스크 페이지를 메모리에 유지한다. fix/unfix는 페이지 사용과 교체 가능 상태를 관리하고, 페이지 latch는 메모리 안의 페이지 접근을 조정한다. BCB는 버퍼 슬롯의 제어 상태이고, VPID는 볼륨·페이지 식별자이다. 페이지 latch와 트랜잭션 lock은 별도 개념이다. dirty 표시나 flush 요청 자체를 트랜잭션 commit 또는 저장 장치까지의 영속화와 같다고 볼 수 없다.

이번 소스 확인 기준은 CUBRID `f6cac312310f39f46711693da157a08f0e725693`이다. 이 기준의 `pgbuf_unfix`에는 빠른 READ 해제 경로와 BCB mutex를 사용하는 경로가 있으며, 후자는 상태에 따라 LRU 관리, 대기자 깨우기, 요청된 flush를 수행한다. 따라서 unfix 한 함수의 짧아진 시간만으로 전체 비용 감소를 결론 내릴 수 없다는 것이 소스에서 도출되는 측정상의 이유이다. 특정 경로가 현재 병목이라는 측정 결과는 아니다. ### 왜 문제인가

SQL 전체 실행 시간에는 페이지 버퍼 외의 실행·접속·대기·I/O 비용도 포함된다. 반대로 직접 fix/unfix 부하만으로는 실제 SQL이 만드는 요청열과 경합을 대표한다고 보장할 수 없다. 두 관측을 연결하지 못하면 국소 개선의 원인을 좁히기 어렵고, 다른 경로로 이동한 비용이나 대표 부하의 회귀를 놓칠 수 있다. 이는 비교 방법의 한계이며, 현재 특정 변경에서 회귀가 발생했다는 주장은 아니다.

기존 세미나 실험은 실제 `pgbuf_fix/unfix`를 호출하지만 CUBRID `f799e05d77d5300c6ea5753b4a6cc7caee6d8912`의 debug SERVER_MODE에 관측 패치를 적용한 동작 검증이다. 최종 실험은 유지보수 callback의 실행을 멈추지만 flush 데몬은 계속 실행한다. trace와 callback 동기화 비용이 포함되므로 그 시간을 비계측 성능 기준으로 재사용할 수 없다. 데이터 준비, 실제 엔진 구동 및 원시 결과·실행 신원 보관 방식은 재사용 가능성을 검토할 자산이다. [실험의 설정·증거 한계](https://github.com/vimkim/my-cubrid-page-buffer-seminar/blob/8dbdff4639734a2eeef327ba9a6343182548b09d/experiments/replacement/README.md)

10/19 회의용 벤치마크 전략은 같은 revision의 비계측 반복으로 편차를 먼저 확인하고 별도 CPU 프로파일을 얻는 순서를 제안한다. 그러나 문서의 합의 기록에는 부하, 머신·빌드, 지표, 역할 및 첫 실행이 미결정으로 남아 있고, 벤치마크 실행이나 개선 수치를 얻지 않았다고 명시한다. 이 검토안을 완료된 합의나 사용 가능한 성능 환경으로 간주하면 비교의 출발점부터 불명확해진다. [전략 검토안과 합의 기록](https://github.com/vimkim/my-cubrid-docs/blob/fd2e244e585de7a78dfccbbdfde722eef1b49210/CBRD-27423/benchmark-strategy-2026-10-19.md), [환경 확인의 한계](https://github.com/vimkim/my-cubrid-docs/blob/fd2e244e585de7a78dfccbbdfde722eef1b49210/CBRD-27423/README.md)

### 왜 해결해야 하는가

실제 엔진 비교를 반복할 수 있으면 페이지 버퍼 변경의 효과와 편차를 구분하고, 관측된 비용을 다음 개선 이슈의 근거로 사용할 수 있다. 개별 실험 자산을 그대로 성능 기준으로 삼는 우회는 빌드·계측·데몬·데이터 조건을 다시 확인해야 하므로 검토 비용을 반복시킨다. 이번 조사는 그 조건과 유효성 판정을 공통으로 정립하기 위한 작업이다. 긴급한 고객 영향이나 정량적인 손실은 현재 근거로 확인하지 못했다.

전체 개선을 기다리는 공통 관문으로 만들 필요는 없다. 결함 이슈의 재현·수정과 이 프레임워크의 공통 비교 기능은 각각 진행할 수 있다. 특정 개선이 이 프레임워크의 새 기능을 실제로 필요로 할 때만 해당 의존성과 이유를 별도로 기록한다.

### 지표 해석의 조건

처리량·wall time·서버 CPU·결과 검증 값을 기본 후보로 두고, 개별 지연 분포, 경합, 교체 탐색량, 비동기 잔여량 및 메모리는 필요한 질문에 따라 추가한다. 배치 소요 시간을 fix/unfix p95/p99로 표현하지 않는다. CPU 프로파일 비중만으로 latch 대기나 mutex 경합을 확정하지 않는다. 도구·권한·수집 오버헤드와 카운터의 정의·단위·활성 조건을 확인해야 한다. 원시 작업량과 작업당 비용을 함께 보고, 의미가 다른 내부 카운터로 두 빌드를 정규화하지 않는다.

현재 기준의 `SHOW PAGE BUFFER STATUS`에서는 Hit_rate·Num_hit·Num_page_request와 생성·쓰기·읽기·대기 관련 총 9개 폐기 열이 항상 NULL이다. 이를 0 또는 유효한 성능 표본으로 사용하지 않는다. 대체로 안내된 statdump 항목도 단위를 확인하여 사용한다. 분석에서는 기존 SQL 실행 자산, 유닛 테스트 기반과 직접 호출 실험의 재사용 가능성·초기화 비용·관측 한계를 비교한다. 선택한 초기 부하에서 실제 엔진의 기준판·변경판을 실행하고 비교할 수 있도록 구현 경계와 검증 방법을 정한다. 구현을 후속 이슈로 분리하면 필요한 능력, 연결 이슈와 이 Survey의 종료 범위를 명시한다. 설계 문서만으로 실엔진 비교 기능이 구현·검증되었다고 처리하지 않는다.

반복 횟수, warm-up 종료, 측정 길이, 계측 도구, 회귀 임계값은 미결정이다. 동일 빌드 A/A 대조로 편차를 확인하고, 비교 도구가 통제된 악화를 드러내는지 점검하는 방법을 검토한다. 모든 부하에 일률적인 수치 기준을 미리 적용하지 않는다. 최적화된 기본 측정과 assertion·상세 trace 실행을 구분하고, 데몬을 정지한 실험은 별도 원인 조사로 표시한다.

일일 CI, 자동 원인 커밋 탐색과 SQL 호출 기록·재생은 확장 후보이다. 도입 여부, 비용, 기준판 갱신과 보관·알림 정책은 합의되지 않았다. 여러 PR이 포함된 revision 비교만으로 특정 PR에 원인을 귀속하지 않는다. 기록·재생을 택하면 VPID·호출 순서 외에 데이터 이미지, dirty/WAL, 할당·해제, 보유 상태, 실패 및 스레드 동기화·간격을 어떻게 보존하는지 먼저 검증한다. 읽기 중심의 제한된 검증부터 시작할지도 ANALYSIS에서 결정한다.

## Acceptance Criteria

- [ ] 초기 부하, 성공 작업 단위, 실제 엔진 구동 방식, 데이터·빌드·환경 조건과 미지원 범위가 근거와 함께 정해져 있다.
- [ ] 실제 엔진의 두 revision을 같은 논리 작업으로 비교하고 원시 결과·실행 신원·실패를 추적할 수 있는 기능과 검증 기준이 정의되어 있다. 구현을 분리한 경우 해당 후속 이슈와 미완료 능력이 명시되어 있다.
- [ ] 동일 빌드 편차, 계측 오버헤드, foreground·데몬·I/O 비용 및 결과 정합성을 구분하여 판정하는 방법이 정해져 있다. 미수집 지표와 비교 불가능한 실행은 명시한다.
- [ ] TPC-H 관련 요청, 유닛 테스트 기반 및 병목을 드러내는 집중 부하를 평가하고 채택·보류 근거를 남긴다. 특정 시나리오 결과를 전체 SQL 성능으로 확대하지 않는다.
- [ ] 구현 범위로 채택한 기능은 지원 환경에서 실제 엔진의 변경 전후 비교 보고서를 재현할 수 있고, 실행별 원시 결과와 오류·timeout·정리 결과를 확인할 수 있다.

## Definition of done

- [ ] Survey 결과에 선택한 초기 범위, 지표 정의, 비교 유효성 기준, 미결정 사항과 후속 구현 경계가 기록되어 있다.
- [ ] 구현한 부분은 프로젝트에서 재현 가능한 절차와 검증 자료로 확인한다. 구현·실행하지 않은 제안은 완료된 기능이나 성능 개선으로 보고하지 않는다.
- [ ] 관련 개선·통계·대표 부하 과제와 공유할 정보 및 실제 선행 조건이 구분되어 있다. 일일 CI·기록 재생 등 보류한 범위와 재검토 조건을 남긴다.
