이 이슈는 페이지 버퍼 EPIC의 벤치마크 수행 하위 작업이다. 버퍼 용량, 동시 접속 수, 스캔 간섭을 각각 바꾸고 실제 페이지 버퍼 부하와 사용자 요청의 성능 변화를 확인한다. 서로 다른 엔진 버전을 비교하거나 특정 페이지 버퍼 개선의 효과를 측정하는 작업은 아니다.

### 왜 이 구분이 필요한가

운영자와 개발자는 동시 요청이 늘거나 스캔이 추가될 때 처리량과 응답시간이 어떻게 변하는지 알아야 한다. 적중률이 높아도 페이지 latch나 객체 잠금을 기다릴 수 있다. DB 페이지 읽기 요청이 늘어도 OS 파일 캐시가 처리하면 물리 저장장치 읽기는 적을 수 있다. 이 값을 구분하지 않으면 개선할 모듈과 검증 조건을 잘못 선택할 수 있다.

이번 측정은 이러한 구분에 필요한 부하·오류·대기 근거를 남겼다. 후속 작업은 확인된 대기 증폭과 아직 설명하지 못한 감속 시작 원인을 구분해 분석해야 한다.

## Errors and Limitations

- 기본 TPC-C의 전체 SQL abort는 A에서 63·67·69건, B에서 381·384·392건이었다. 모두 엔진 오류 -72이며 성공 완료율에서 제외했다. 첫 쌍의 서버 교착 알림·-72 기록·클라이언트 abort 수는 같은 300초 구간에서 일치했다. 예상 밖 SQL 오류는 없었다. 의도한 rollback은 SQL 오류와 별도 집계했다.
- sysbench 무시 오류·재연결, 음수 카운터 델타, 조건 종료 시 정리 오류와 잔여 소유 native 프로세스는 기본 18조건 모두 없었다. 스캔 결과도 검증했다.
- 시작 전 quiet gate를 통과했지만 공유 호스트의 간섭을 완전히 배제하지 못했다. 기본 일부 구간에 소량의 전역 swap 전송이 겹쳤다. TPC-C 2·3쌍은 전역 swap 0에서도 큰 지연 증가를 재현했다. 단회 개입에는 전역 swap 43,499페이지가 겹쳤으며 그 발생 주체는 확인하지 못했다.
- 기본 성능 비교와 진단 실행은 별도이다. 랜덤 조회의 동일 이미지 계측 비교는 3쌍을 확보했지만 일부 구간의 swap과 반복 변동이 남았다. 짧은 TPC-C·스캔 계측 비교는 각 1쌍이다. 후반 감속 상태의 정확한 계측 비용은 분리하지 못했다.
- CPU sample 손실과 커널 심볼 제한이 있었고 off-CPU tracepoint는 사용할 수 없었다. CPU 표본의 함수 비중을 잠든 요청의 대기 시간으로 해석하지 않는다. 비활성 victim 카운터의 0도 victim 활동 부재의 근거로 쓰지 않는다.
- 각 기본 비교는 합의한 3쌍의 관측이다. 통계적 일반화, 다른 데이터 크기·mix·장시간 실행·릴리스 버전의 영향은 검증하지 않았다. WAL·flush·checkpoint와 개별 직렬화의 독립적인 기여도 남아 있다.

## Conclusion

1. 세 부하에서 실제 페이지 버퍼 활동과 성능 변화를 측정했다. 용량 축소와 스캔 간섭은 반복 가능한 영향을 보였지만, 이번 조건에서 페이지 버퍼 자체를 주된 병목으로 확정할 근거는 부족하다.
2. TPC-C 32클라이언트에서 큰 감속이 반복되었다. 객체 잠금 대기·교착·실패 SQL과 단일 설정 개입을 함께 보면, 교착 해소 주기에 따른 객체 잠금 대기 증폭이 이 감속에 기여한다는 근거가 있다.
3. 약 180초 뒤 전환을 시작하는 전체 원인과 각 자원의 기여는 미확인이다. 0.1초 설정을 운영 기본값으로 제안하거나 페이지 버퍼 변경의 해결 효과로 보고하지 않는다.
4. 이 하위 작업은 벤치마크 수행과 조사 결과 정리의 산출물로 판단한다. 조사 결과가 엔진 수정 완료나 전체 원인 규명 완료를 뜻하지 않는다. 이슈 종료 여부는 이 범위와 한계를 검토해 결정한다.
