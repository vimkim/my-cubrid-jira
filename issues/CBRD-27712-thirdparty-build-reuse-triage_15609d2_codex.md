## Description

### 무엇이 문제인가

QA 팀 강태우님은 현재 CI에서 3rdparty 빌드가 전체 빌드 시간의 대부분을 사용하고 네트워크 비용도 발생한다는 이유로 개선 검토를 요청했다. 이 요청은 CUBRID 소스가 바뀌었을 때마다 변경되지 않은 의존성까지 다시 준비하는 비용을 줄일 필요가 있음을 보여준다.

CUBRID를 빌드하려면 CUBRID 소스뿐 아니라 Expat, OpenSSL, RE2 등 3rdparty 의존성도 준비해야 한다. 기존 기본 빌드는 의존성의 산출물과 준비 상태를 CUBRID build 디렉터리에 함께 보관한다. 기준 소스의 `3rdparty/CMakeLists.txt`는 의존성 작업의 기준 경로를 `${CMAKE_BINARY_DIR}/3rdparty`로 지정한다.

개발자가 build 디렉터리를 삭제해 빌드 상태를 초기화하거나, 새 worktree의 별도 build 디렉터리에서 빌드를 시작하면 의존성 준비 상태도 새로 시작한다. 의존성 버전과 빌드 환경이 같더라도 완성된 의존성을 별도로 지정해 쓰는 공통 기능이 없으면 해당 작업 공간에서 준비를 반복하게 된다. cubridci에서도 이미 준비한 의존성 산출물을 활용할 수 있어야 같은 비용의 반복을 줄일 수 있다.

이번에 필요한 기능은 3rdparty를 CUBRID와 분리해 빌드하고, 완성된 헤더·라이브러리 등을 모은 디렉터리의 경로를 CUBRID 빌드에 지정하여 재사용하는 것이다. 이 디렉터리를 prefix라 부른다. 같은 의존성을 사용하는 개발 로컬 빌드와 cubridci가 이 기능을 활용할 수 있도록 한다.

모든 증분 빌드에서 의존성이 다시 빌드되거나 매번 전체 다운로드가 발생한다고 전제하지 않는다. 문제를 제기하는 조건은 준비 상태를 다시 만들어야 하는 빌드이며, 재다운로드 여부는 아카이브 보존 상태 등에 따라 달라진다. CI에서 실제로 반복되는 단계와 각 단계의 비용은 분석에서 확인한다.

### 왜 문제인가

개발자가 버그를 재현하거나 수정 결과를 검증할 때 필요한 것은 CUBRID 변경에 대한 결과다. 변경하지 않은 의존성을 준비하는 작업이 다시 들어가면 검증을 마치기까지 대기가 늘고 CPU·디스크 자원도 사용한다. 여러 수정안을 별도 worktree에서 검증할수록 같은 환경의 반복 준비가 누적될 수 있다.

cubridci에서는 이 비용이 여러 변경의 빌드와 검증에 반복해서 영향을 준다. 강태우님이 현재 CI 시간의 대부분을 차지한다고 지적한 3rdparty 준비 단계는 빌드 시간 단축을 위해 검토해야 할 주요 병목이다. 이 단계의 산출물을 재사용하면 준비 작업의 반복을 줄일 수 있으므로, 전체 빌드 시간을 크게 단축할 수 있는 개선 지점이다.

의존성을 반복해서 내려받아 준비하는 경로에서는 같은 입력을 확보하는 데 네트워크도 계속 사용한다. 준비된 산출물을 재사용하면 반복 다운로드와 configure·빌드를 줄일 수 있다. CI에 산출물을 공급하는 데 필요한 전송량까지 포함한 실제 네트워크 절감 규모는 적용 방식을 정하고 측정해야 한다.

기존 build 디렉터리를 유지하는 방법은 로컬에서 일부 재준비를 피하는 데 도움이 된다. 그러나 build 상태를 완전히 초기화하거나 다른 worktree·CI 빌드에서 사용해야 하는 요구를 충족하려면, 의존성 산출물을 CUBRID build 디렉터리의 수명과 분리해 지정할 수 있는 기능이 필요하다.

CI 빌드 시간의 대부분을 차지한다는 내용과 네트워크 비용은 사용자가 전달한 QA 측 검토 요청에 근거한다. 이번 문서 작성에서 단계별 시간이나 전송량을 새로 측정하지 않았으며, 기존 로컬 검증 기록도 CI 개선율의 측정 근거로 사용하지 않는다.

### 왜 해결해야 하는가

QA 팀의 개선 검토 요청으로 현재 CI의 구체적인 병목과 비용 문제가 제기되어 있다. 반복 준비를 그대로 두면 로컬 개발자가 변경 결과를 기다리는 비용뿐 아니라 cubridci가 여러 변경을 빌드할 때 사용하는 시간과 자원도 계속 소모된다. 이미 준비한 의존성을 반복해서 만드는 작업을 줄이는 것은 개발과 QA가 함께 활용할 수 있는 개선이다.

3rdparty 분리 빌드와 경로 지정 재사용 기능을 제공하면, 의존성이 바뀌지 않은 빌드에서 준비를 생략하고 CUBRID 빌드와 검증을 진행할 수 있다. 개발자는 clean 재빌드와 worktree 전환을 더 가볍게 수행할 수 있고, cubridci는 준비된 의존성을 재사용하여 주요 준비 단계의 반복을 줄일 수 있다. 그 결과 로컬 검증과 CI 피드백을 더 빨리 받을 수 있다.

이 기능을 공통 빌드 인터페이스로 제공하면 개발자와 CI가 각각 별도의 우회 방법을 만드는 부담도 줄어든다. 재사용 가능한 컴파일러·플랫폼·의존성 구성과 변경 시 처리 기준을 함께 정리하여, 속도 개선과 올바른 빌드 결과를 함께 확보해야 한다.

분리 빌드와 경로 지정 재사용은 이번 요청에서 정한 기능 범위다. cubridci에서 산출물을 어떤 방식으로 보관하고 공급할지, 어느 환경 사이에서 재사용을 허용할지, 구체적으로 얼마나 절감되는지는 ANALYSIS에서 결정·확인한다. 일반 Linux 경로의 unixODBC 설치 정책은 기존에 연결된 CBRD-27711과 구분해 다룬다.
