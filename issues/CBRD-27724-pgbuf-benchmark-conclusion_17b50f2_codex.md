페이지 버퍼 개선의 우선순위를 정하려면 실제 부하를 만들고, 그 부하에서 요청이 왜 느려지는지를 확인해야 한다. 본 실험은 동일한 CUBRID 엔진에서 버퍼 용량, TPC-C 클라이언트 수, 대형 스캔의 동시 실행을 각각 바꾸었다. 각 비교는 예열 120초와 측정 300초로 3쌍 반복했다. 기본 성능 측정과 요청 분류 진단은 별도 실행으로 구분했다.

버퍼를 8GiB에서 512MiB로 줄인 비교의 처리량 하락 중앙값은 4.0230%였고, hot 조회에 스캔을 추가한 비교는 9.2668%였다. 두 조건은 페이지 버퍼 압력을 발생시켰지만 사전에 합의한 큰 저하 기준에는 못 미쳤다. TPC-C 클라이언트를 8개에서 32개로 늘린 비교에서는 foreground 비rollback 완료율이 중앙값 17.6013% 감소하고, New Order 완료 p99의 조건별 중앙값은 21ms에서 858ms로 증가했다.

TPC-C의 대기 카운터·교착 로그·실패 SQL을 조사한 뒤, 교착 탐지 주기만 1.0초에서 0.1초로 줄이는 개입을 수행했다. 개입 1회에서 New Order 비rollback 완료율은 기본 32클라이언트 3회 중앙값 350.300/s에 비해 862.230/s였고, p99는 858ms에 비해 77ms였다. 평균 객체 잠금 대기도 줄었으나 abort 비율은 증가했다. 이 결과는 교착 해소 주기에 따른 객체 잠금 대기 증폭의 기여를 지지한다. 페이지 버퍼 자체가 주된 병목이라는 결론과 약 180초 뒤 감속을 시작하는 원인은 이번 자료로 확정하지 못했다.

## 1. Introduction

### 1.1 페이지 버퍼 부하와 요청 지연은 같은 현상이 아니다

페이지 버퍼는 DB 페이지를 서버 메모리에 보관하여 반복 접근에서 파일 읽기를 줄인다. 버퍼가 작아지거나 대형 스캔이 많은 페이지를 읽으면 필요한 페이지가 버퍼에서 빠질 수 있다. 그러나 페이지를 다시 읽는 비용이 곧바로 저장장치 접근 비용이 되는 것은 아니다. DB 서버 밖의 OS 파일 캐시가 읽기를 처리할 수 있기 때문이다.

요청이 필요한 페이지를 메모리에서 찾았더라도 다른 트랜잭션과 충돌하면 객체 잠금을 기다릴 수 있다. 페이지 버퍼 적중은 그 페이지의 소재에 대한 답이며, 트랜잭션이 해당 객체를 즉시 사용할 수 있다는 답은 아니다. 따라서 높은 적중률과 긴 응답시간이 함께 나타날 수 있다.

| 구분 | 답하려는 질문 | 요청 성능을 해석할 때의 의미 |
| --- | --- | --- |
| 페이지 버퍼 적중·미스 | 기존 페이지를 처음 확인할 때 서버 버퍼에 있었는가 | 버퍼 내 소재를 설명한다. latch나 객체 잠금 대기 부재를 보장하지 않는다. |
| 페이지 latch 대기 | 페이지를 안전하게 접근하는 데 필요한 보호를 바로 얻는가 | 페이지가 resident여도 발생할 수 있는 대기이다. |
| 객체 잠금 대기 | 다른 트랜잭션과 충돌하지 않고 해당 객체에 접근할 수 있는가 | 데이터가 메모리에 있어도 트랜잭션 진행을 막을 수 있다. |
| DB 페이지 읽기 요청 | 엔진이 페이지 읽기를 요청했는가 | OS 캐시가 응답할 수 있으므로 물리 저장장치 읽기와 다르다. |

상위 페이지 버퍼 개선 작업에서 필요한 것은 이 경로 중 어느 비용을 줄여야 하는지 판단할 근거이다. 본 연구는 부하 발생과 성능 저하를 확인한 뒤, 카운터·실행 경로·개입 실험으로 설명을 좁히는 방식으로 접근했다. 모든 느려짐을 페이지 버퍼의 결함으로 전제하지 않았다.

### 1.2 연구 질문

첫 번째 질문은 접근 가능한 데이터보다 버퍼를 작게 만들었을 때 읽기 요청과 사용자 성능이 얼마나 달라지는가이다. 두 번째는 갱신을 포함한 트랜잭션의 동시성을 높였을 때 어떤 대기가 커지는가이다. 세 번째는 버퍼보다 큰 스캔을 hot 조회와 함께 실행하면 hot 요청에 어떤 간섭이 생기는가이다.

세 질문을 나눈 이유는 조건마다 비용이 발생하는 경로가 다르기 때문이다. 용량 비교는 같은 읽기 부하에서 버퍼 크기를 바꾼다. 동시성 비교는 같은 초기 데이터에서 동시에 진행하는 트랜잭션 수를 바꾼다. 스캔 비교는 같은 hot 요청에 추가 부하를 가한다. 이 구분이 있어야 결과가 달라졌을 때 어느 변화와 연결되는지 설명할 수 있다.

## 2. Methods

### 2.1 동일 엔진과 통제 조건을 사용한 이유

기본 엔진은 `17b50f29760eab9017dcfdb2b47571878463380e`로 고정했다. 비교 중 기본 엔진 소스를 바꾸지 않았다. 따라서 결과는 코드 변경 전후의 회귀가 아니라 동일한 구현이 서로 다른 부하 조건에서 보인 동작이다.

공유 Linux 호스트 dev2에서 작업 전용 DB·설치·설정을 사용했다. `release_gcc` 설치를 사용했고, 서버·CAS에는 NUMA node 1의 서로 다른 물리 코어 16개, 클라이언트에는 별도 물리 코어 4개를 배치했다. 배치는 비교 양쪽에서 유지했으나 코어를 독점 예약한 것은 아니다. 시작 전 quiet gate로 외부 CPU·NVMe 사용·메모리·swap·I/O pressure를 확인했고, 측정 중에도 공유 호스트 간섭을 기록했다.

각 조건에서 서버를 다시 시작하여 서버 버퍼 상태를 새로 준비했다. TPC-C는 매 조건 전에 같은 초기 백업을 복원했다. 앞선 실행이 갱신한 데이터를 다음 조건의 출발점으로 사용하지 않기 위해서이다. 다만 클라이언트의 난수 트랜잭션 순서까지 동일하게 재생하지는 않았다. OS 파일 캐시는 비우지 않았다. 따라서 이 실험은 저장장치까지 비운 cold-cache 실험이 아니다.

### 2.2 세 부하가 검증하려는 것

| 실험 | 데이터와 고정 조건 | A와 B에서 바꾼 항목 | 이 설계를 선택한 이유 |
| --- | --- | --- | --- |
| 용량 비교 | 3,294,000행, heap·index 3.980GiB, 읽기 클라이언트 8개 | 버퍼 8GiB와 512MiB | 전체 데이터보다 큰 버퍼와 작은 버퍼를 대조하여, 같은 SQL에서 residency와 읽기 요청이 달라지는지 본다. |
| TPC-C 동시성 비교 | 16개 창고, heap·index 2.035GiB, 버퍼 1GiB, 같은 초기 백업 | 클라이언트 8개와 32개 | 읽기만으로 드러나지 않는 갱신·객체 잠금·로그 기록 비용이 동시성 증가에 따라 커지는지 본다. |

용량과 hot 조회에는 회사 CCI 드라이버를 사용하는 sysbench 부하를 사용했다. 키를 균등하게 뽑아 약 90%는 `SELECT SUBSTR(c,1,1) ... WHERE id=?`, 약 10%는 연속 16행의 `SELECT SUM(k) ... WHERE id BETWEEN ? AND ?`를 실행한다. 각 이벤트 뒤에 COMMIT을 수행한다. 단건 조회가 heap의 값을 실제로 읽게 하되 반환량을 한 글자로 줄여, 큰 결과 전송이 비교를 지배할 가능성을 줄였다. seed는 27724로 고정했다. 90:10은 두 조회 형태를 고정 비율로 섞는 실험 조건이며, 운영 업무에서 측정한 분포나 최적 비율을 뜻하지 않는다.

TPC-C에는 회사 BenchmarkSQL 5.0 구현을 사용했다. New Order, Payment, Order Status, Stock Level, Delivery의 가중치는 45:43:4:4:4이다. 인위적인 pacing 없이 실행했고, 8개와 32개 모두 16개 창고를 같은 범위에서 선택했다. 창고 수를 클라이언트 수와 함께 늘리면 데이터와 충돌 조건도 바뀌므로, 이 비교에서는 창고 수를 유지했다. 공식 TPC 인증 점수를 산출하려는 실행은 아니다.

New Order는 district를 `FOR UPDATE`로 읽어 주문 번호를 갱신하고 주문을 삽입한다. 이어 5~15개 품목의 stock을 `FOR UPDATE`로 읽어 재고와 주문 상세를 갱신한 뒤 commit한다. Payment는 창고·district·고객 정보를 갱신하고, 다른 트랜잭션은 주문·재고 조회나 배송 처리를 수행한다. 따라서 이 부하는 같은 테이블에 대한 단순 읽기만이 아니라 여러 객체를 거치는 트랜잭션 간 충돌을 포함한다.

스캔에는 TPC-H의 Q1과 Q6을 사용했다. Q1은 출하일 조건을 만족하는 행을 상태별로 묶어 수량·금액 등의 집계를 계산하고, Q6은 출하일·할인율·수량 조건에 맞는 할인 매출을 합산한다. 저장한 계획에서 두 쿼리 모두 순차 스캔을 사용했다. hot 클라이언트와 별도 JDBC 연결 하나가 Q1과 Q6을 번갈아 순차 실행했다. hot 조회와 스캔이 동시에 실행되며 Q1과 Q6끼리는 동시에 실행되지 않는다.

준비 때 결과 해시와 실행계획을 저장하고, 스캔을 추가한 실행에서도 결과와 측정 구간 내 완주를 확인했다. 비교할 사용자 성능은 hot 조회의 처리량과 응답시간으로 한정했다. 스캔을 추가한 만큼 전체 요청 수가 늘어난 것을 hot 성능 향상으로 세지 않기 위해서이다.

여기서 데이터 크기는 접근 가능한 heap·index의 크기이다. 실제 방문한 고유 페이지 전체를 직접 센 working set 크기와 같지는 않다. 특히 트랜잭션마다 접근 경로와 재사용 빈도가 다른 TPC-C에서 두 크기를 동일시하지 않는다.

### 2.3 예열·반복·실행 순서를 둔 이유

각 실행은 예열 120초와 측정 300초로 구성했다. 초기 연결과 버퍼 준비가 한 번의 짧은 수치를 좌우하는 영향을 줄이고, 일정 시간 지속되는 동작을 보려는 프로토콜이다. 부하마다 A 후 B, B 후 A, A 후 B의 순서로 3쌍을 수행하여 시간 순서와 공유 호스트 상태가 항상 한 조건에만 유리하게 작용하는 것을 줄였다. 세 부하의 총 기본 측정 조건은 18개이다.

각 쌍의 A를 분모로 처리량 하락률 `(A-B)/A*100`과 p99 증가율 `(B-A)/A*100`을 계산했다. 보고하는 변화율 중앙값은 이 세 쌍의 중앙값이다. A 조건들의 중앙값과 B 조건들의 중앙값을 먼저 구한 뒤 나눈 값이 아니다.

사전에 합의한 큰 저하 기준은 세 쌍 모두 같은 방향의 변화가 나타나고, 쌍별 중앙값이 처리량 10% 이상 하락 또는 p99 20% 이상 증가하는 것이다. 이 기준은 상세 원인 조사의 대상을 고르는 기준이다. 기준을 넘었다고 원인이 자동으로 증명되거나, 못 미쳤다고 영향이 없다고 판정하지 않는다. 통계적 유의성 검정을 대체하는 기준도 아니다.

실행 뒤에는 이 프로토콜의 중요한 한계가 드러났다. TPC-C 32클라이언트는 약 180초 뒤 감속하여, 측정 300초 안에 전환 전후가 함께 들어갔다. 따라서 예열이 끝난 뒤 모든 실행이 정상 상태에 도달했다고 가정하지 않고 시간별 결과도 분석했다.

### 2.4 성공·오류·지연의 분모

sysbench 처리량은 완료 이벤트/s이다. 한 이벤트의 SELECT와 COMMIT을 두 개의 처리로 세지 않는다. TPC-C에서는 SQL 오류가 없는 완료 요청에서 의도한 rollback을 뺀 값을 비rollback 완료율로 사용한다. p99는 SQL 오류가 없는 완료 요청의 99번째 백분위 응답시간이며, 의도한 rollback은 포함한다. 따라서 처리량과 p99의 모집단은 정확히 같지 않다.

TPC-C의 foreground 완료율은 다섯 트랜잭션 종류의 합이며 `DELIVERY_BG`는 더하지 않는다. 이 도구는 Delivery 접수와 실제 처리의 기록을 `DELIVERY`와 `DELIVERY_BG`로 나눈다. 실제 사용한 구현에서는 같은 terminal이 처리를 이어서 수행하므로, 이를 별도 배경 워커의 실행으로 설명하지 않는다. 접수 기록을 포함한 합계가 물리 WAL commit/s를 뜻하는 것도 아니다.

실패가 빠르게 반환되면 전체 시도 수는 늘어도 유용한 처리는 늘지 않을 수 있다. 이를 피하기 위해 SQL abort를 성공 완료율에서 제외하고 의도한 rollback과도 분리했다. 실제 오류 기록을 보완한 클라이언트 CSV와 서버 로그를 같은 시간 구간에서 대조했다.

### 2.5 성능 실행과 요청 분류 진단을 나눈 이유

성능 비교는 진단 카운터를 추가하지 않은 기본 엔진으로 수행했다. 실제 hit·miss의 의미를 확인하는 실행은 진단 소스 `1a9805db9aaeb7a143644932f3db8ad001c72656`에서 별도로 수행했다. 계측 자체가 성능과 실행 시점을 바꿀 수 있기 때문이다. 서로 다른 실행의 처리량과 적중률을 같은 구간의 값처럼 합치지 않는다.

실제 적중은 기존 페이지를 사용하려는 성공 요청의 첫 확인에서 페이지가 서버 버퍼에 있었던 경우이다. 다른 요청이 읽어 오는 동안 기다렸다면 미스로 센다. 신규 할당, 실패, resident 여부만 확인하는 probe는 따로 센다. 일반 경로와 임시 페이지 경로를 각각 집계한 뒤 `적중/(적중+미스)*100`으로 계산했다. 한 번의 파일 읽기를 여러 요청이 기다릴 수 있으므로, 요청 미스 수와 DB 읽기 요청 수는 서로 다를 수 있다. 같은 페이지를 다시 접근할 때도 매번 요청으로 세므로, 이 적중률은 고유 페이지 수의 비율이나 버퍼 용량을 데이터 크기로 나눈 비율과 다르다.

신규 할당, cold 읽기, hot 읽기, 동시 loader 대기, 임시 spill·probe, 예상 query timeout의 여섯 사례로 실제 엔진 경로를 보정했다. 분류 합계와 전체 요청 수를 대조했다. 기존 엔진의 hit ratio와 DB 읽기 요청 카운터도 보존했지만, 이를 새 정의의 실제 적중률로 대신하지 않았다.

결과는 큰 스캔의 추가가 hot 요청에 반복적인 간섭을 만든다는 것을 보여 준다. 그 간섭은 버퍼 재사용 변화, 스캔의 CPU·메모리·I/O 사용 등 여러 경로로 설명될 수 있다. 이번 비교는 스캔의 유무만 바꾸었으므로 그 내부 비용을 각각 분리하지는 못했다. hot 페이지의 퇴출이 유일한 원인이라는 결론은 근거를 넘는다. 관측한 간섭은 후속 조사 대상으로 보존하되, 사전에 정한 큰 저하 기준에 못 미친 결과로 해석한다.

서버·CAS·Java의 평균 CPU 사용은 배정한 전체 코어를 포화시키지 않았다. 따라서 전체 코어의 CPU 부족만으로 긴 tail을 설명할 근거는 약하다. 개별 스레드의 직렬화나 통신 비용까지 배제하지는 않는다.

## 4. Mechanism and Intervention

### 4.1 관측을 설명하는 가설을 어떻게 세웠는가

동시 트랜잭션이 많아지면 같은 객체에 대한 잠금 충돌이 겹칠 수 있다. 갱신 트랜잭션은 앞서 얻은 잠금을 유지한 채 다음 잠금을 기다릴 수 있다. 그 잠금이 필요한 다른 요청도 기다리게 되면 지연이 여러 요청으로 이어질 수 있다. 교착은 이러한 의존관계가 순환하여 관련 트랜잭션들이 스스로 진행하지 못하는 상태이다.

탐지기가 순환을 찾고 피해 트랜잭션이 중단·rollback하여 잠금이 풀리면 다른 요청이 진행할 수 있다. 서버 작업 스레드는 그동안 `lock_suspend`에서 기다린다. 따라서 교착을 해소하는 주기가 길면 순환이 생긴 뒤 풀릴 때까지의 대기가 전체 지연을 키울 수 있다. CPU를 계속 사용하지 않는 이 대기는 CPU 포화 없이도 긴 응답시간을 만들 수 있다.

이번 자료에서는 동시성 증가, 객체 대기 증가, 실제 교착·-72, 관련 SQL이 함께 관측되었다. 여기서 세운 가설은 '교착 해소 주기가 관측한 긴 객체 잠금 대기를 증폭한다'이다. 이 가설이 맞다면 다른 조건을 유지한 채 탐지 주기를 줄였을 때 평균 객체 대기와 성공 요청의 지연이 줄어들 것으로 예상할 수 있다.

이 설명은 교착이 처음 만들어진 경로를 모두 밝혔다는 뜻이 아니다. 실제 도구는 New Order의 stock 접근을 공급 창고·품목 순서로 정렬한다. 그러므로 임의 순서로 두 stock을 반대로 잠갔다는 단순 예를 이번 교착의 확인된 원인으로 쓰지 않는다. 어떤 트랜잭션 조합과 상태 변화가 약 180초의 전환을 시작하는지는 별도 질문이다.

### 4.2 가설을 시험하기 위해 바꾼 것

| 전체 종류 SQL abort | 384건 | 1,900건 |
| New Order abort/시도 | 0.3550% | 0.7142% |

평균 대기와 성공 요청 지연은 예상한 방향으로 줄었고 성공 완료율은 늘었다. 3.4절의 구간별 결과에서도 후반의 큰 감속이 완화되었다. 대기 카운터, 실제 실행 경로와 개입의 방향이 함께 맞는다는 점이 단순한 동시 발생보다 강한 근거이다.

### 4.3 실패를 빨리 반환하여 좋아 보인 결과인가

개입의 전체 abort 1,900건은 New Order 1,879건과 Payment 21건이며 모두 -72이다. 예상 밖 SQL 오류는 없다. 실제 도구는 이 오류를 기록하고 rollback한 뒤 다음 트랜잭션으로 진행한다. 실패한 동일 요청을 자동으로 다시 실행한 결과로 세지 않는다.

New Order의 개입 측정 구간에는 263,091개 시도가 있었다. 여기서 abort 1,879개와 의도한 rollback 2,543개를 제외한 비rollback 완료는 258,669개이다. 이를 300초로 나눈 값이 862.230/s이다. 따라서 빠른 실패를 성공 수에 섞어서 만든 개선은 아니다. 반면 abort/시도 비율 자체도 약 두 배가 되었으므로 실패 비용이 늘었다는 관측을 함께 유지한다.

대기 횟수가 증가한 것도 평균 대기가 늘었다는 뜻은 아니다. 개입에서는 더 많은 트랜잭션이 진행하면서 더 많은 충돌·대기 사건을 만들 수 있다. 이번에는 사건 수가 늘고 1건당 시간이 줄었다. 원시 횟수 하나만으로 더 나빠졌거나 좋아졌다고 판단하지 않고 성공 완료율, 응답시간, 대기 시간과 실패 비율을 함께 본 이유이다. 탐지 주기와 abort 증가의 세부 관계를 이 단회 실험으로 모두 분리한 것은 아니다.

### 4.4 높은 적중률은 객체 대기 해석과 모순되지 않는다

후반 감속을 재현한 별도 32클라이언트 진단은 New Order 비rollback 356.737/s, 완료 p99 845ms였다. 이 실행의 303초 카운터 구간에서 일반 적중 102,527,640회와 미스 484,753회로 실제 적중률은 99.5294%였다. 신규 성공 23,900회와 demand 실패 43,445회는 분모에서 제외했고, 전체 요청 103,079,738회와 분류 합계가 일치했다.

이 값은 페이지를 처음 확인할 때 이미 서버 버퍼에 있던 성공 요청이 많았다는 뜻이다. 해당 트랜잭션이 객체 잠금을 즉시 얻었다는 뜻은 아니다. 동일 페이지를 반복 접근하면 요청 수에 가중된 적중률은 높을 수 있으며, 적은 수의 비싼 미스나 다른 대기의 존재도 이 비율만으로 배제할 수 없다. 실제로 이 진단은 높은 적중률과 느린 트랜잭션을 같은 실행에서 관측했다.

또한 이 비율은 해당 진단 서버의 모든 수집 요청을 대상으로 한다. 기본 18조건의 적중률, 특정 SQL의 적중률, 방문한 고유 페이지의 비율로 바꾸지 않는다. 이 근거에서 도출할 수 있는 것은 높은 적중률만으로 병목을 배제할 수 없으며, 이번에는 객체 잠금 대기 경로를 별도로 조사할 필요가 있었다는 판단이다.

## 5. Discussion

### 5.1 관측에서 결론으로 가는 근거

| 판단 단계 | 사용한 근거 | 도출할 수 있는 판단 | 남는 질문 |
| --- | --- | --- | --- |
| 실제 부하가 있었는가 | 용량 축소의 읽기 증가와 별도 residency 진단, 스캔 완주·결과 검증, TPC-C 실제 트랜잭션 | 세 조건 모두 계획한 작업이 실제 실행되었다. | 접근 가능한 데이터 전체와 방문한 고유 페이지는 같지 않다. |
| 큰 저하가 반복되는가 | 부하별 기본 A/B 3쌍과 변화 범위 | TPC-C 32클라이언트가 상세 조사 기준을 충족했다. | 다른 데이터·기간에서도 같은 크기로 나타나는가. |

| 그 경로의 조건을 바꾸면 예측이 맞는가 | 탐지 주기만 줄인 개입의 지연·평균 대기 감소 | 교착 해소 주기가 대기를 증폭한다는 설명을 지지한다. | 단회·공유 호스트 효과를 제외한 반복 크기와 최적 설정은 무엇인가. |

이 연결 때문에 결론은 객체 잠금 대기 증폭의 기여에 둔다. 페이지 버퍼에 부하를 주었다는 사실만으로 페이지 버퍼 구현을 원인으로 선택하지 않았다. 반대로 페이지 버퍼 비용이 전혀 없다고 배제한 것도 아니다. 용량과 스캔은 실제 영향을 보였고, TPC-C에서도 페이지 접근 비용과 다른 자원의 독립적인 기여는 남아 있다.

### 5.2 왜 CPU 프로파일만으로 결론을 정하지 않았는가

CPU 프로파일의 함수 비중은 CPU에서 실행 중인 비용을 보여 준다. 객체 잠금을 기다리며 잠든 시간 전체를 보여 주지는 않는다. `pgbuf_fix_release` 같은 함수가 상위에 보인다는 사실만으로 수백 ms의 요청 지연을 그 함수에 귀속할 수 없다. 이번에는 별도 PID 프로파일 여섯 개를 수집했지만 sample 손실과 커널 심볼 제한도 있었다. 그래서 대기 카운터·서버 로그·SQL과 개입 실험을 함께 사용했다.

WAL·flush·checkpoint·유지보수의 활동과 쓰기 부하도 관측되었다. 그러나 이들 중 무엇이 객체 대기의 전환을 먼저 유발했는지, 각각이 전체 느려짐의 얼마를 차지하는지는 분리하지 못했다. 후반 읽기·쓰기 요청 수가 감소했다는 사실도 처리량 감소의 결과일 수 있으므로, 그 자원이 원인이 아니라고 단정하는 데 쓰지 않는다.

## 6. Threats to Validity

### 6.1 반복과 호스트 간섭

기본 비교는 각 3쌍이며 통계적 일반화를 위한 다수 반복이나 유의성 검정은 수행하지 않았다. 개입은 1회이다. 기본 일부 구간은 소량의 전역 swap 전송과 겹쳤다. TPC-C 2·3쌍은 전역 swap 0에서도 큰 지연 증가를 보였다. 개입에는 전역 swap 43,499페이지가 겹쳤으며 발생 주체를 확인하지 못했다. 설정 한 변수를 통제했어도 호스트의 모든 상태까지 통제한 것은 아니다.

따라서 개입은 가설을 지지하는 관측이며, 모든 대안 설명을 제거한 최종 인과 증명은 아니다. 0.1초를 일반적인 운영 최적값으로 권고하지 않는다. abort 증가까지 고려해 같은 초기 이미지의 교차 반복과 더 긴 관측이 필요하다.

### 6.2 계측과 시간 구간

성능 측정 300초와 statdump 301~304초는 경계가 다르다. 별도 진단은 기본 반복의 적중률을 대신하지 않는다. 랜덤 조회의 동일 이미지 계측 비교는 3쌍을 확보했지만 일부 swap과 작은 반복 변동이 남았다. 짧은 TPC-C·스캔 계측 비교는 각 1쌍이며, 약 180초 이후 감속 상태의 정확한 계측 비용은 분리하지 못했다.

CPU sample에는 손실이 있었고 off-CPU tracepoint는 사용할 수 없었다. 비활성 victim 카운터의 0을 victim 활동 부재로 해석하지 않았다. 이러한 자료 품질 때문에 각 자원의 비용을 정밀하게 분해한 결론은 내리지 않는다.

### 6.3 오류와 재현 범위

기본 TPC-C 전체 SQL abort는 A 63·67·69건, B 381·384·392건이다. 모두 -72이며 성공 완료율에서 제외했다. 예상 밖 SQL 오류는 없었다. sysbench 무시 오류·재연결, 음수 카운터 델타, 조건 종료 시 정리 오류·잔여 소유 native 프로세스도 기본 18조건 모두 없었다. 의도한 rollback은 오류와 별도 집계했다.

실험은 고정 빌드·회사 도구·해당 데이터·선택 코어의 결과이다. 다른 릴리스, 다른 트랜잭션 mix, OS 캐시 해제 조건과 장시간 실행에 그대로 적용하지 않는다. 원본 DB·전체 로그·부하 도구를 묶은 공유 첨부는 아직 없으며, 원본 보존과 다른 사람이 전체 실행을 재현할 수 있는 배포 패키지는 구분한다.

## 7. Conclusion

본 연구는 버퍼 용량 축소, 갱신 트랜잭션의 동시성 증가, 대형 스캔 간섭을 분리해 페이지 버퍼 부하와 요청 성능을 비교했다. 세 부하의 기본 A/B 각 3쌍을 완료했고 실제 실행·오류·요청 분류와 결과를 검증했다.

용량 축소는 읽기 요청과 미스를 늘렸지만 처리량 저하는 약 4%였다. 물리 읽기가 작고 OS 캐시를 유지했다는 관측이 이 차이를 설명하는 근거이다. 스캔 추가는 hot 성능을 약 9% 낮췄지만, 전체 적중률만으로 hot 페이지 퇴출의 기여를 분리할 수는 없었다.

TPC-C 32클라이언트에서는 큰 지연과 객체 잠금 대기가 반복되었다. 실제 교착·실패 SQL·대기 경로를 확인한 뒤 탐지 주기를 줄이자 성공 완료율, 완료 p99와 평균 객체 대기가 예상한 방향으로 바뀌었다. 따라서 가장 강한 결론은 이 부하에서 교착 해소 주기에 따른 객체 잠금 대기 증폭이 성능 저하에 기여한다는 것이다. 단회 개입과 공유 호스트 간섭 때문에 기여의 크기와 일반성에는 한계가 있다.

약 180초 뒤 감속을 시작하는 전체 원인과 페이지 버퍼 자체의 주병목 여부는 미확인이다. 이 이슈의 산출물은 벤치마크 수행과 근거를 갖춘 조사 결과이며, 엔진 수정이나 전체 원인 규명 완료를 뜻하지 않는다. 후속 질문과 분리하여 이 하위 작업의 완료 범위를 검토한다.

## 8. Follow-up Analysis

첫 후속 질문은 약 180초 시점에 무엇이 먼저 바뀌는가이다. 보존한 분 단위 클라이언트 결과, 객체 잠금·교착, WAL·flush·checkpoint, dirty 페이지와 페이지 버퍼 대기를 같은 경과 시간에 정렬해 선후 관계를 좁힌다. stock 실패 위치와 전체 교착의 발생 경로도 구분해 추적한다.

추가 실험이 승인되면 동일 초기 이미지에서 탐지 주기 1.0초와 0.1초를 교차하여 최소 3쌍 비교하고 전환 이후를 더 길게 관측한다. 시간·자원 한도와 호스트 간섭 기준은 새 실행 전에 정한다. 성공 완료율, abort 비율, p99와 시간별 대기를 함께 비교해야 한다. 이 제안은 추가 실행이나 일정의 확정이 아니다.
